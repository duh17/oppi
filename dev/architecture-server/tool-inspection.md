# Oppi server architecture: Tool inspection

Part of [Oppi server architecture](../architecture-server.md). Producer facts, the mobile-renderer registry, and full tool-output ownership.

## Tool inspection facts

`MobileRendererRegistry` owns tool identity and matches Pi's exact tool name. Its focused modules own collapsed segments (`mobile-renderer-segments.ts`), input/output facts (`mobile-renderer-facts.ts`), display names (`mobile-renderer-display.ts`), and availability (`mobile-renderer-availability.ts`). The registry keeps sidecar loading and invalid-warning deduplication in one place; there is no second registry. Built-in `bash` and arbitrary renderer sidecars declare command fields through `inputPresentation.fields` (`role: "command"`, `language: "shell"`) and terminal output through `outputPresentation.kind`. Session protocol projection and trace replay consume these facts; neither keeps a shell-name list. History resolves facts from the current registry even when summary segments are not requested.

Built-in read/write/edit declare `filePath`, `fileContent`, `edits` (oldText/newText pairs), and optional `lineOffset`/`lineLimit` roles. Output kinds `fileContent` and `diffOfEdits` carry optional `provenance: requested | result`; write content is requested, read content and result diffs are results. Args-derived edit previews remain requested. Sidecars can declare the same facts for any exact tool name. Apple models tolerate missing/unknown fields.

Explicit result `details.outputPresentation` overrides the static declaration. `details.expandedText` also overrides it: terminal format keeps terminal semantics; other formats emit structured semantics so clients clear an earlier terminal declaration. Unknown explicit kinds degrade to structured output. When both producer-fact fields are absent, the sole OppiCore compatibility resolver synthesizes native facts for exact `bash`, `read`, `write`, `edit`, and `ask` names. It never synthesizes availability or setting authority. Other tools without facts use generic inspection.

## Full output and snapshot lifetime

Result `outputAvailability` projects Pi truncation and full-output-source availability as `{ complete, totalBytes?, source? }`. The optional source is `"sidecar"`, never a filesystem path. Live and history publication strip `details.fullOutputPath` and path-bearing truncation members after deriving availability; the original details remain server-owned for sidecar lookup. A source fact permits tool-call-ID reads but does not promise the file survives a stopped session. Terminal-kind output no longer uses tail previews or replace mode; see [Terminal output byte stream](#terminal-output-byte-stream). HEAD/Range and JSON read Pi's file when present, otherwise Oppi's current uncut runtime snapshot. Pi file paths are captured on updates as well as completion. `ToolOutputSnapshots` in `tool-output-sidecar.ts` owns each runtime's in-memory uncut output and the tool-end-to-trace handoff. The protocol translator calls this owner instead of maintaining a partial-result map. Pi-truncated snapshots remain delta baselines and cannot be served as full output. Oppi keeps its complete handoff snapshot until `turn_end`, after Pi has appended results; subsequent endpoint reads can use complete trace text. Truncated trace text never substitutes for a missing Pi file. Input roles, output semantics, and completeness are independent facts carried through live events and trace replay.

## Terminal output byte stream

A call whose `outputPresentation.kind` is `terminal` (resolved by `MobileRendererRegistry`, never by tool name) streams as one append-only raw byte log. `TerminalOutputStreams` (`terminal-output-stream.ts`, owned by `ToolOutputSnapshots.terminal`) is the only owner. It is driven synchronously from the protocol translator: no `fs.watch`, async pump, Pi `onData`/`customTools` hook, or server-side terminal engine.

Wire (additive optional fields; no new message type, no base64, `tool_output` stays ephemeral):

- `tool_output.outputStream = { epoch, offset, bytes }`. `output` is the UTF-8 decoding of exactly `bytes` raw bytes, codepoint-complete, with VT sequences **not stripped**. Offsets count raw bytes and are never derived from `output` (it may contain U+FFFD). Stream chunks carry no `mode`, `truncated`, `totalBytes` or `outputAvailability`.
- Within an epoch chunks are strictly contiguous from offset 0. A larger epoch means "discard prior state" and restarts at offset 0.
- `tool_end.outputStream = { epoch, totalBytes }` is the final length of the final epoch. Pi's trailing result text (status lines, truncation footer) is not stream bytes when a Pi file exists.
- Attach ready marker: when a focused stream binds (initial attach and reconnect), after catch-up replay and the queued live drain, the server sends one zero-length `tool_output` (`bytes: 0`, `offset` = bytes already sent) per running terminal stream. Finished streams get no marker. The terminal mirror runtime does not provide markers; its clients resolve on the next chunk.
- `GET /server/info` `capabilities.sessionStream.version` is 2. Clients older than version 2 would append raw VT text as plain output; there is no compatibility layer.

Sources, in order:

1. **Before Pi names a temp file** the cumulative `partialResult` text is the log (its UTF-8 encoding). Text that extends the previous text appends. Text that does not (a status view replaced) bumps the epoch. The retained text is also the sidecar snapshot (served even when Pi flags its own view truncated), so Range returns exactly the bytes sent.
2. **Once `details.fullOutputPath` is known** `partialResult` text is ignored and the file is read from the cursor with bounded `readSync`. The first file read verifies `file[0, sent) == sentBytes`. A file shorter than what was sent (Pi's write stream lags the update) waits for a later tick; a mismatch (for example invalid UTF-8 that Pi's decoder replaced) bumps the epoch and restarts from file byte 0. A trailing partial codepoint at end of file is held until completed. Until that check succeeds the sidecar keeps serving the retained streamed text: the coordinator does not publish the file path for the call, and the snapshot is not dropped when it ends unverified.
3. **At `tool_execution_end`** the remainder is drained, then `totalBytes` is reported from the verified file size (or the log length without a file). A named file that never became the verified log (unreadable, or still shorter than what was sent) is not reported as a finished short log: `totalBytes` is the larger of the producer's `truncation.totalBytes` and the bytes sent, the streamed text stays servable until `turn_end`, and a single `terminal_stream.file_read_failed` error log (tool call id and errno code, never the path) is logged. The client gap-fills and ends visibly unresolved if the sidecar cannot serve the rest. Without a file, the final result text is reconciled against the log (prefix: append the tail; otherwise bump the epoch).

Bounds: chunks are at most 64 KiB and codepoint-aligned; at most 256 KiB is emitted per Pi update tick (Pi already throttles updates to 100 ms; there is no extra throttle). The end drain is capped at 4 MiB; when more remains, `totalBytes` exceeds what was sent and the client fills the gap from the sidecar. The stream is dropped at tool end; a no-file log stays in `ToolOutputSnapshots` until `turn_end` so Range reads between tool end and trace append see the same bytes.

Non-terminal kinds keep `computeToolOutputUpdate` cumulative deltas, replace mode, and ANSI stripping unchanged.

## Setting authority and outline projection

The registry also declares `outputPresentation.settingEffect: "voiceReplyMode"` for session-setting producers. Explicit result details can override content semantics, but cannot grant themselves a setting effect. Managed events, mirror events, and history use the same declaration.

Lightweight trace outlines use this registry too. They carry input/output facts, display metadata, and optional path/command/range/edit arguments and selected result details so clients outside the local trace window do not classify raw tool names. File-content and code blobs are excluded. Optional arguments and retained result details share a 64 KiB per-request budget with an 8 KiB per-object cap; over-budget metadata is omitted, never truncated. The compact result path avoids decoding result content; the noncompact JSON fallback temporarily decodes the entry before discarding its content. Details are inspected one entry at a time before retaining only the projected content fields. Entry-local semantic hints preserve registry-derived output overrides and MCP display inputs independently of content eviction; declaration-owned setting effects are attached when the result is associated with its tool. Outline summaries and display labels have a 160-character ceiling. Clients retain the producer summary when arguments are absent. Compaction is a separate session entry, not a synthetic tool.

Neither the session runtime nor the terminal mirror captures Pi tool-result TUI render snapshots. Generic output with empty text renders structured result details using the client document renderer. This does not remove the separate terminal mirror runtime or its owner-socket protocol.
