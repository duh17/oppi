# Oppi server architecture: Session runtime

Part of [Oppi server architecture](../architecture-server.md). Runtime ownership, the managed SDK runtime, saved Agents and schedules, and the terminal mirror.

## Session runtime ownership

`SessionRuntimes` is the server facade for runtime-owned operations. It dispatches by persisted `Session.runtime`:

- `"oppi"` routes to managed `SessionManager` and the in-process Pi SDK backend.
- `"pi-tui"` routes to `PiTuiMirrorRuntime` and the terminal bridge.

The facade handles common calls such as prompt, steer, follow-up, abort, stop, queue state, pending UI, event catch-up, snapshots, and full tool-output paths. Route and stream code should prefer `SessionRuntimes` when the command applies to either runtime owner.

A stopped, disconnected mirror session with a canonical session file can be promoted to `"oppi"` on resume or focused-stream open. A connected or stale terminal-owned session stays terminal-owned. A terminal bridge can take over an existing `"oppi"` session only after explicit terminal confirmation; if that session is active, the server stops the managed runtime before switching ownership.

## Managed SDK runtime

`SessionManager` is the managed runtime facade. It keeps active sessions in memory and delegates most behavior to coordinators from `session-coordinators.ts`:

- `SessionStartCoordinator` creates SDK-backed active sessions.
- `SessionActivationCoordinator` handles start/resume idempotence.
- `SessionInputCoordinator` handles prompt, steer, follow-up, attachment validation, and first-message capture.
- `SessionMessageQueueCoordinator` owns steering/follow-up queue state.
- `SessionCommandCoordinator` forwards SDK commands and applies SDK snapshots.
- `SessionAgentEventCoordinator` translates Pi events into server messages.
- `SessionBroadcaster` assigns per-session sequence numbers and supports focused-session catch-up.
- `SessionStopFlowCoordinator` and `SessionStopCoordinator` own abort/stop behavior.
- `SessionLifecycleCoordinator` handles idle timers and session end cleanup.

`sdk-backend.ts` wraps Pi's `AgentSession`. It resolves workspace cwd, configures sandbox tools when requested, binds extensions through `SdkUiBridge`, injects session attachment helpers, forwards SDK commands, and emits Pi events back into the session projection pipeline. Declared control sessions use an owner-only, non-symlink `$OPPI_DATA_DIR/control-sessions/cwd` as the real Pi SessionManager cwd. They otherwise use ordinary Pi global configuration and resources. `Pi Control` remains display metadata only and must not be persisted as SessionManager cwd, or Pi JSONLs land under the server process working directory and leak into workspace importable-local discovery. Sandboxes still keep their guest/display cwd split with a host existence override.

The managed pipeline uses the `AgentBackend` interface in `server/src/agent-backend.ts` for commands, queue authority, lifecycle transactions, and runtime snapshots. `SdkBackend` implements this seam and keeps the live Pi `AgentSession` inside the adapter. Both managed backends reuse the sandbox VM owner exposed by `SdkBackend.ensureSandboxWorkspaceVm()`. Session creation selects the SDK unless the session is enrolled in the experimental server-durable backend.

## Server durable (experimental)

`oppi config set experimental.serverDurable true` makes durable sessions available after a server restart; it never enrolls a session by itself. A session runs on `DurableBackend` only when its create request asks for `engine: "durable"` (`POST /workspaces/:id/sessions`, `oppi session create --engine durable`). An omitted engine, or `"classic"`, is the SDK backend; quick actions, control sessions, imports, forks of classic sessions, and scheduled or Quick Session launches without the field stay classic. Saved Agents cannot start durable sessions yet: `POST /agents/:id/sessions` (and `oppi session create --agent <x> --engine durable`) with `engine: "durable"` is HTTP 400 before any session row exists, and the Apple Durable Quick Session hides its Agent picker. Asking for durable while the flag is off fails with HTTP 409 and no session; an unknown engine is HTTP 400. A durable request the backend would refuse at start (incognito, a sandbox workspace with MCP servers; `durableUnsupportedFeature` is the one list both use, and the backend also refuses a saved Agent that selects Extensions) is HTTP 400 before any session row exists. An idempotent replay that asks for the other engine than the stored session is HTTP 409. `SessionManager.durableSessionsAvailable()` reads the startup flag, and `GET /server/info` advertises `capabilities.durableSessions: { version: 1 }` only while it is on. `SessionSummary.engine` is `"durable"` for durable sessions and omitted for classic ones; full `Session` payloads mark the durable engine with `serverDurable`. The SQLite list projection keeps `server_durable_json` and reconciles it with `session_json` on every open. Child sessions that `oppi.sessions` spawns are created bound to their conversation, so they are durable without a request field. The flag is absent by default. Existing SDK and terminal sessions do not change. A bound durable conversation cannot switch between host and sandbox execution, or move to another sandbox workspace.

`DurableHarness` opens one process-owned Harness lazily at `$OPPI_DATA_DIR/durable/harness.sqlite`. It adopts the server's `ModelRuntime` — the same `auth.json` and `models.json` runtime that already carries global provider-extension registrations, including Anthropic OMP — plus global `SettingsManager` run policy, CodingTools (read/write/edit/bash), and a Node execution environment for each host cwd. A private runtime is only for tests and callers that have not discovered extensions. Production open fails if that shared runtime was not bound. Sandbox conversations persist their execution boundary in `oppi.execution-runtime` and attach a `GondolinExecutionEnv` before scheduling resumes. An unattached sandbox fails closed instead of falling back to host execution. It reuses the manager's per-workspace VM, keeps file tools inside `/workspace/<slug>`, and never forwards the host shell environment. Guest ls/find/grep use the existing sandbox operations; a sandbox-only read wrapper returns image content. Every shell/search execution uses `setsid` and kills its guest process group on cancellation or timeout. A pre-exec stream handshake captures the guest pgid and process starttime in host memory before launch; cancellation waits for the identity-checked group kill and reports failures. Guest root can replace `/bin/sh` or `/usr/bin/setsid` on the VM's writable root and forge the next handshake; that root can already signal any guest pid. A descendant that calls `setsid` leaves the captured process group: Stop kills the original group and confirms while the new session keeps running. Environment cleanup cancels its calls but never stops the shared VM. The shared session-status path holds the VM while a runtime is attached and allows idle teardown after Stop or error. Session-local model and thinking choices persist through `configure()`. `Session.serverDurable` records enrollment and the conversation ID before the first submission. Apple `clientTurnId` becomes Durable `requestId`; command correlation IDs do not. Native reporters reserve request ID prefixes through `durable-request-ids.ts`; client turn IDs using those prefixes are rejected before admission.

Committed events pass through `durable-event-adapter.ts` to the existing Pi event projection and Oppi sequence ring. State and queue reads use `pi.agent`, `pi.live`, `pi.usage`, and `pi.inbox`. Startup aborts all task scopes of stopped conversations, including background tasks, and withdraws their queued inputs while the shared scheduler is paused, then attaches resumable conversations and calls `resume()`. Crash healing queues live idle sessions too, so their conversation-owned background work can resume. It rechecks the restart queue before each attach and after cancellation awaits so an explicit stop or deleted workspace wins. The Harness scheduling gate is held from construction through startup resolution. Stops use paused task/submission cancellation while it is held; prompts and compaction fail with a retryable startup error instead of waiting while holding admission permits. Failed input admission leaves restart intent intact. Native inbox reconciliation reserves rich queue metadata before submission, then commits or discards it with admission so broadcasts preserve attachment references without duplicate chips. Both crash recovery and graceful restart continue the original submission without a restart continuation prompt. Explicit stops abort unfinished work. Shutdown detaches conversations recorded for restart without aborting them, and aborts only those that must stay stopped before closing storage. Unsafe tools interrupted by a crash report interruption; they do not automatically rerun their side effects.

Live assistant text is projected from Durable partials as append-only deltas. If a provider assigns non-prefix text after a longer prefix was already sent (for example, an OpenAI Responses done-item replacement or a `text_end` replacement), the live bubble can show appended text until `message_end` replaces it with canonical content. Trace history reads committed entries and is unaffected. Replacing an in-flight bubble requires a protocol change.

A durable input that settles `unanswered` for a reason other than `aborted` or `withdrawn`, and a faulted or orphaned task that is not compaction and not the generation whose inputs already settled, is recorded as a display-only transcript card (`data.card`, accent `error`) with no model messages. The write uses a reserved `oppi-failure:` request id, so a retry is the same card. Attach reconciles a crash between settlement and that write by reading unanswered inputs and terminal tasks. History (full trace, page, and outline) shows the card at the write position. An assistant entry with `stopReason: "error"` does not carry `errorMessage` into the trace, so the card is the history row unless that same text is already visible assistant text. The live `error` for the settlement stays the in-session row; a history reload replaces the timeline with the card, and the failure card does not also emit a notice.

Host durable sessions load Pi's MCP servers through `durable-mcp.ts`, which reuses Pi's MCP config loader, connections, credentials, naming, and result conversion from `pi-mcp-internals.ts` and replaces only the classic glue. Each attachment owns one registry extension, `oppi.mcp/<sessionId>`, that `DurableHarness` installs, reinstalls in place when a server's tool list changes, and uninstalls on Stop or shutdown. The Harness default extension selection is pinned to the base extensions, so an `{ add }` selection never picks up another session's MCP extension. A project `.pi/mcp.json` loads only after `resolveManagedProjectTrust` through the startup UI bridge, as for SDK sessions. `direct` tools are appended to the conversation's explicit tool list; `codemode` (Pi's `codemode` built-in does not exist on durable) and `deferred` tools are reached through a durable `tool_search` that returns `control.addTools`, so loaded tools persist in `pi.agent`. The first prompt waits up to 10 s for servers whose tools it offers, and attaching a busy conversation waits for startup connections before resume so recovered calls find their tools. MCP tools replay after a crash only with `readOnlyHint` or `idempotentHint`. Startup problems are one `notify` warning; signed-in servers reconnect before the next prompt.

Durable sessions install native `ask`, `working-words`, and `background-jobs` extensions from `pi-extensions/<name>/durable.ts`. A committed `oppi.extension-ui` conversation document supplies pending dialogs and persistent UI through the existing extension UI projection. Pending asks survive process restart and accept the first committed answer; Abort and Stop cancel them. Background shell jobs belong to the conversation and survive ordinary Stop. Bash waits up to 15 seconds before returning a background-job notice; a trailing `&` backgrounds immediately. Jobs run in the conversation's host or sandbox execution environment. Restart reports an interrupted execution without rerunning the shell. Each job persists a `background-job:<id>` follow-up receipt. Queued receipts remain undelivered; withdrawn or mismatched receipts advance to a persisted `background-job:<id>:<n>` ID. Delivery requires matching content and a placed or done receipt, then clears the retained output atomically. Results are not combined into classic-style batches, and widgets show final output only. See [Durable extension UI](durable-extension-ui.md) for the document convention, loading, and proof commands.

Durable sessions can spawn child sessions through the native `oppi.sessions` extension (`server/extensions/durable/sessions/durable.ts`): `session_spawn`, `session_send`, `session_wait`, `session_abort`. Ownership is the Harness's, and it is the only record of who spawned whom. A foreground child is a conversation owned by the `session_spawn` tool task, so the parent stays busy until the child is idle and Stop reaches it through the cascade. A background child is owned by a background anchor task; Stop does not reach it, and a background reporter task hands it its task and posts its answer to the parent as a follow-up. Request IDs make a restart deliver each once: `oppi-spawn:<taskId>` (the child's first task), `oppi-report:<taskId>` (the report) and `oppi-send:<taskId>` (`session_send`). They are reserved in `durable-request-ids.ts`. `session_send` and `session_wait` take any session bound to a durable conversation, except that a sandbox caller reaches only sandbox sessions of its own workspace (checked from the persisted `DurableRuntime` docs before anything attaches, prompts or waits); `session_abort` only stops a conversation the caller owns, and a child cannot spawn. A full Stop of a session (not a composer abort) also aborts its `oppi.session-reporter` tasks (`DurableHarness.abortSessionReporters`), so a stopped parent gets no new turn from a background child's report; the child and background shell jobs keep running. `DurableThreads` (`durable-threads.ts`) gives each owned child its Oppi Session: created exactly once, keyed by the child conversation id (launch idempotency key `durable-thread:<conversationId>`), bound through `serverDurable.conversationId` with the parent's workspace, worktree and runtime, and attached, so a restart finds it in `resumeIds`. A row already holding that key is adopted only when it is bound to that same conversation; otherwise the spawn fails, and session create routes reject `durable-thread:` keys from clients. `launch.parentSessionId` is a write-once copy of the ownership edge. `GET /sessions/:id/thread` for a durable session adds the sessions its ownership edges put in the thread (`scanConversations({ ownerConversationId })`, from the topmost owner down; when that owner's Session is gone, the thread roots at the nearest remaining ancestor Session) to the launch-edge tree, so a child belongs without a launch edge and a session the phone starts in the thread still joins through its launch edge; the response shape is unchanged. Classic sessions keep the launch-edge tree and `session_interactions`.

The durable control conversation is one Session row per data directory, marked `serverDurable.role: "control"` and bound to its conversation id, created on demand by `POST /control-conversation` (`oppi control open|send`) through `ControlConversationService` under the reserved launch key `control-conversation`. It selects an exact extension array (`controlConversationExtensions`: `ask`, `working-words`, `oppi.control`), never `baseExtensions`, re-asserted on every attach, and runs in the owner-only `$OPPI_DATA_DIR/control-conversation/cwd`. Idle, it is on the restart-resume queue and comes back after a restart. It is on the phone's global recent list with declared control sessions, never in a workspace catalog or count, and the phone opens it through the same `/control-sessions` routes. List rows carry `serverDurable.role` so the client can tell it from a workspace durable session; the conversation id stays off that projection. `oppi.control` (`server/extensions/durable/control/durable.ts`) registers `oppi_query` and `oppi_script`, which run model-written JavaScript in pi-codemode's `CodemodeSandbox` with defaults (the server runs unbundled). The sandbox has one table of globals: `oppi(argv)` and typed wrappers that only build argv. `DurableControlCli` (`server/src/durable-control-cli.ts`, bound with `DurableHarness.bindControl`) is the host the extension cannot import. It refuses argv that reaches the host without a request or would hurt the server it runs in (file flags, `@-`, `config set`, `--config-file`, the `control` family, which would message the conversation from inside its own turn, `status`, which shells out synchronously on the event loop, and the `--idempotency-key=`, `--request-id=` and `--turn-id=` forms, which the CLI ignores and the host cannot tell from a script's own key). For `agent create`, `session create`, `schedule create` (`--idempotency-key`), `schedule run` (`--request-id`), and `session send` (`--turn-id`) it makes `<taskId>:<call index>:<hash of the call's argv>` the only replay key, replacing any key the script passed; the hash keeps a rerun whose calls came out in another order from giving one write another write's key. It runs `runCli` with `forceJson` and `captureHuman` inside `withLocalApiInterceptor`. The interceptor throws on a non-GET for `oppi_query`; for `oppi_script` it awaits the extension's confirm card, which is a `select` through `requestUI` and is asked one card at a time. A PATCH card carries a diff against the record the host fetches. The gate is fixed in code. `oppi_script` is `replay: "safe"`: every call's result, reads included, is memoized by call index (`oppi-call:<n>`, with its argv), so a rerun after a crash follows the data the first run saw and returns finished calls instead of running them again, and a call whose argv changed fails the script. Before each confirm card is asked, the request it shows (method, path, body) is memoized under its slot (`oppi-card:<index>.<n>`, first write wins), so a saved answer, including one restored by "Yes to all", belongs to that request: a rerun that reaches the slot with a different write fails with `card_changed` and sends nothing. `oppi_query` keeps nothing. A confirm card shows the whole request body; a body over 6000 characters is refused (error `body_too_large`, nothing asked or sent) instead of truncated. Each script runs under a 24 h deadline (the sandbox default of 5 minutes would cancel an unanswered card and cut `sessions.wait` short) and a 256 MiB VM memory limit. The same prompt section also holds the rendered declarations and is asserted to stay under 2 KiB.

Replay is exactly-once only for the five keyed commands above (`session start` is `session create`), and only when a rerun gives each call the same call index. The replay key comes from the call index, so a rerun whose calls complete in a different order (for example under `Promise.all`) can raise a fresh card for a keyed write that already landed: the owner is asked again, and approving repeats the write. A repeated `clientTurnId` (what `--turn-id` becomes) is deduplicated by a durable conversation from its stored submission, which survives a server restart; a classic session dedupes it in the in-memory turn cache (15 minutes, 256 entries), which a restart loses. Residual risks of slice 1:

- `agent update` and `agent archive` have no replay key. After a crash between the write and its memo, the rerun reports a false failure (a version conflict, or 404 for an archived Agent); with `expectedVersion` the patch is not applied twice, so wrappers should pass it. Without it an `append` instruction patch applies twice.
- Escape-hatch writes through `oppi(...)` that have no key (workspace and worktree create or open, dictionary add, schedule update) can be applied again after a crash in that window.
- Every call's envelope is memoized, reads included, and the task record is rewritten with all memos at each commit. There is no cap on that size.
- A transport error after the server applied a write is memoized as a failure, so a rerun does not retry it with its key.
- `config show|get|validate` build a `ConfigStore` that may rewrite `config.json` under a synchronous spin lock of up to about 5 s on the server's event loop.
- Replay keys are not scoped to one durable store. If the durable database were reset while the Agent and Schedule stores kept their data, a new task could reuse an old key with the same argv and get an old record back.
- Confirm cards are answered with owner or paired-device credentials as `extension_ui_response`, over the WebSocket `/control-sessions/<sessionId>/stream` or `POST /control-sessions/<sessionId>/command` (and `POST /sessions/<id>/command`); `GET /sessions/<id>/dialogs` lists the pending card and its id. The phone lists the row with declared control sessions and answers the card with the existing select dialog. There is no CLI verb for the answer.
- The confirm card guards against the control model, not against other local processes that hold the owner token: those could write through the API directly anyway.

This slice has a minimal coding prompt plus workspace and saved-Agent instructions. Classic extensions, sandbox MCP (selected sandbox MCP servers fail with `server_durable_not_supported`), tree navigation, export, and entry renderers are unavailable. `reloadResources` loads AGENTS files and saved-Agent skillPaths; it does not load classic extensions, prompt templates, or themes. Queue editing is a full replacement of steer and follow-up inbox items: removed submissions settle `unanswered`/`aborted` so the original send stays quiet, write items stay queued, and a boundary that places an item during the edit rejects the stale save. The edit does not start a turn. Idle sessions still cannot gain a queue from nothing, and an idle rewrite waits for the next real admission, which places writes before the new input. Fork uses the Durable `conversation.fork(entryId)`: `get_fork_messages` lists user-message entries by their decimal Durable entry ids (the ids of the trace's user rows), and the fork route creates a new bound Session on a forked, ownerless conversation that keeps the source's execution runtime. As in classic fork, the branch point is the visible entry before the chosen user message, so the fork's transcript ends before it (the phone does not read the message text back as editor text). Forking at the first user message has no earlier entry, so it creates a fresh ownerless conversation with the source's stored agent and runtime. A durable source never falls back to a Pi JSONL fork. Unsupported backend operations throw `DurableNotSupportedError` (`server_durable_not_supported`). Saved Agents that explicitly select Extensions and incognito sessions are rejected rather than silently losing those guarantees. Apple history paging and outline read Durable entries. `compact()` is implemented; retry toggles still throw, and full compaction/retry detail parity remains outside this slice. Turning the flag off rejects new durable requests; already-bound Durable sessions keep resuming on Durable without it, and a durable request that never bound a conversation starts classic with a session warning.

## Saved Agents and schedules

Saved Agent routes persist reusable user definitions. The Agents client presents Pi separately, without an `agent_definitions` row. Launch-time inputs such as workspace, worktree, prompt, model override, and session name flow through `AgentLaunchService`, which owns idempotency, launch recovery, target-constraint enforcement, and prompt dispatch into managed sessions. Definitions may restrict launches to allowed workspace IDs and a required host or sandbox runtime. Incompatible targets and unavailable selected Skills or Extensions fail closed as typed configuration failures. Allowed tool names that no active tool matches at launch are dropped from the session's effective tool set and surfaced through `session.warnings`, so an unavailable allowlist entry cannot block the whole launch; the saved definition is not rewritten. Pre-start checks may discard a never-announced empty shell and return an actionable non-retryable `422` without a session ID; failures after runtime start preserve one `error` session for audit. Focused streams close with policy violation rather than reconnecting and duplicating timeline errors.

A server-scoped Pi Control session persists explicit `domain`, `intent`, and optional target metadata with no `workspaceId`. Creation may set model and thinking overrides, while a user-selected workspace remains prompt context rather than runtime ownership. `/control-sessions` routes admit a declared control session or the durable control conversation before reusing the ordinary lifecycle, trace, attachment, command, broadcaster, and focused-stream services. Both remain in the global recent projection but never enter workspace catalogs or counts. An idempotent launch persisted as `promptDispatch: not_sent` may claim a compare-and-swap lease and retry its frozen initial prompt. A launch left `launching` after process failure is conservatively not redispatched even after lease expiry, because existing persistence cannot distinguish a crash before send from one after Pi accepted the turn. Agent, Schedule, Workspace, and Skill revisions use explicit control domains rather than inferring authority from a missing workspace. Pi Control loads normal global `SYSTEM.md`, `APPEND_SYSTEM.md`, settings, tools, Skills, prompt templates, and Extensions. It has ordinary host-user permissions and can run the installed `oppi` CLI through `bash`; Oppi does not add a separate tool approval layer.

The CLI accepts bounded in-memory `--definition-json` objects for Agent create/update and schedule update, avoiding temporary files for those domains. Canonical Agent and schedule validators reject unexpected fields and empty updates at the server boundary. Skill revisions instead use stock `read` and `edit` on the selected existing absolute host path. The `oppi skill` CLI family and Skill-file HTTP PUT route do not exist; catalog editability remains presentation metadata, not a stock-tool authorization boundary.

Schedules persist a trigger plus an action. `AgentScheduleRunner` scans active schedules, materializes due slots, claims due runs with a lease, and dispatches automatic runs through the same launch hooks used by manual schedule runs. Pause or archive a schedule to stop future automatic runs. Archived schedules remain listable and can be restored directly to active.

## Terminal mirror runtime

`PiTuiMirrorRuntime` owns `/mirror/v1/bridge` and implements the same `AgentRuntimeTransport` interface as the managed runtime. It registers terminal bridges, resolves the workspace, coalesces sessions by Pi identity, handles takeover confirmation, forwards remote commands, proxies extension UI, mirrors queue state, and projects terminal Pi events through the shared session event pipeline.

Mirror sessions are terminal-owned. If the bridge disconnects, the stored session remains `runtime == "pi-tui"` unless the app explicitly resumes a stopped disconnected session as an Oppi-managed runtime.
