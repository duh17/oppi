# Oppi server architecture: Session runtime

Part of [Oppi server architecture](../architecture-server.md); same standard (owners, boundaries, invariants, entry points).

## Runtime ownership

`SessionRuntimes` (`runtime-router.ts`) dispatches runtime-owned calls by persisted `Session.runtime`: `"oppi"` → `SessionManager` and the in-process backends, `"pi-tui"` → `PiTuiMirrorRuntime`. Route and stream code use it for any command that applies to either owner.

- A stopped, disconnected mirror session with a canonical session file may be promoted to `"oppi"` on resume or stream open; a connected or stale one stays terminal-owned. A bridge takes over an `"oppi"` session only after explicit terminal confirmation, and the managed runtime stops first.

## Managed SDK runtime

`SessionManager` keeps active sessions in memory and delegates to coordinators (`session-coordinators.ts`): start, activation (idempotent start/resume), input, message queue, commands, agent events, `SessionBroadcaster` (per-session sequence numbers, catch-up), stop flow, lifecycle (idle timers, cleanup). The `AgentBackend` seam (`agent-backend.ts`) carries commands, queue authority, lifecycle transactions, and snapshots; `SdkBackend` (`sdk-backend.ts`) keeps the live Pi `AgentSession` inside the adapter.

- `session-work-root.ts` is the one owner of a session's host directory (workspace mount or worktree, control cwd). Start and attachment writes ask for creation; reads and cleanup never create directories.
- Declared control sessions use the owner-only, non-symlink `$OPPI_DATA_DIR/control-sessions/cwd` as the real Pi cwd. `Pi Control` is display metadata only and is never persisted as a cwd: Pi JSONLs would land under the server's working directory and leak into importable-local discovery.
- `GondolinManager` derives a VM's read-only Skill mounts at boot, one per workspace `.pi/skills` entry; they are not part of the VM fingerprint, so a new entry waits for the next boot.
- A sandbox session offers only Skills the VM can serve (`loadSandboxSkills`, `durable-project-resources.ts`); a selection the VM cannot serve fails `agent_skills_unavailable`. Classic turns off host Skill discovery, including `keepSandboxSkillDiscoveryOffHost`: Pi's package manager otherwise walks `.agents/skills` from `/` synchronously with no cycle guard, and session creation fails if Pi changes that shape. Context files come through the VM (`readVmTextFileWithin`, 1 MiB).
- Classic sandbox `/skill:` is expanded by an inline `input` handler (`createSandboxSkillCommandExtension`) through `GondolinExecutionEnv.readSkillFile`. A VM refusal is returned as `handled`, never thrown: `emitInput` would swallow the throw and Pi would `readFileSync` the guest path on the host.

## Server durable (experimental)

- `experimental.serverDurable` makes durable sessions available; it never enrolls one. A session is durable only when its create request says `engine: "durable"` (workspace sessions, saved Agents, schedule actions); omitted or `"classic"` is the SDK backend. Durable while the flag is off → 409; unknown engine → 400; a feature durable refuses (`durableUnsupportedFeature`, the one list) → 400 before any row exists; an idempotent replay naming the other engine → 409. Children spawned by `oppi.sessions` are bound at creation.
- The flag is latched at startup and changed only by the settings route's save (`setDurableSessionsAvailable`), so `GET /server/durable-sessions/settings` reports what the process does. Every server constructs `DurableHarness` because Oppi Control is durable everywhere, so `capabilities.conversationStream` and the durable extension routes always exist. Turning the flag off rejects new durable requests; bound sessions keep resuming on durable.
- A bound conversation never switches between host and sandbox or moves to another sandbox workspace.

### Harness and stores

- `DurableHarness` (`durable-harness.ts`) is the process-owned runtime: the server's `ModelRuntime`, registry, package reload, run-policy settings, and extension lists. Production open fails if the shared runtime was not bound.
- Each root session tree has a `SessionHost` store at `$OPPI_DATA_DIR/durable/sessions/<rootSessionId>/` (`meta.json`, `session.sqlite`, proper-lockfile directory lock). The host closes when nothing is attached, subscribed, or live in its task graph. Conversation ids are per store and `Session.serverDurable.storeId` is the root session id; a row without `storeId` cannot open as durable. Each Oppi Control session has its own store.
- `SessionHost` builds each conversation's services from the Harness alone (no `Session`, no classic frames): `host.controller()` (`DurableAgentController`) owns request-id dedupe, the content fingerprint (`oppi.request-content`), the admission chain, and the input failure card; `host.models()` (`DurableModels`); `host.transcript()`. Every client input goes through the controller, so a request id is admitted once whichever path sends it, and changed content under a used id is rejected.
- `DurableBackend` is the classic-event facade the session socket still reaches through `AgentBackend`; it delegates to those services. Moving iOS and Mac to `Transcript` deletes the facade, `durable-event-adapter.ts`, and the event projection.
- Apple `clientTurnId` becomes the Durable `requestId`. Native reporters reserve prefixes in `durable-request-ids.ts`, and client turn ids using them are rejected.

### Sandbox execution

A sandbox conversation persists its boundary in `oppi.execution-runtime` and attaches a `GondolinExecutionEnv` before scheduling resumes. An unattached sandbox fails closed and never falls back to host execution or forwards the host environment. Every shell or search runs under `setsid` and its guest process group is killed on cancel or timeout, after a pre-exec handshake records pgid and starttime. Residual: guest root can replace `/bin/sh` or `setsid` and forge the handshake, and a descendant that calls `setsid` escapes the group. Environment cleanup never stops the shared VM.

### Startup, restart, and failure

- Startup reopens the stores of sessions in the resume queue, aborts leftover tasks of conversations whose rows are neither active nor queued (scheduler paused), then attaches and resumes. It rechecks the restart queue before each attach and after awaits, so an explicit stop or deleted workspace wins. Prompts and compaction during startup fail with a retryable error instead of holding admission permits.
- Crash recovery and graceful restart continue the original submission without a continuation prompt. Explicit stops abort unfinished work. Unsafe tools cut off by a crash report interruption and never rerun their side effects.
- Live text and thinking stream as append-only deltas; a non-prefix rewrite sends `replace: true` (older clients append, as before).
- Failed inputs and faulted tasks become display-only failure cards under a reserved `oppi-failure:` request id. The card commit is queued before any await, so a prompt sent right after cannot land ahead of it. Attach reconciles missed cards through `Storage.scanSubmissions` (never a second connection or pi-durable's private tables), tracked by the `oppi.failure-cards` high-water mark; a failed scan fails the attach. `DurableBackend` emits one `prompt_error` per failed run.
- Each Harness's `onReport` logs `durable_store.report` for failures that do not fail the calling operation.
- Stores migrate to pi-durable schema 2 (pi-durable 1.4.0); 1.3.0 cannot open them, so a downgrade past that pin loses durable sessions. `restartLimit: Infinity` keeps 1.3.0's behaviour because Oppi's long in-process waits (reporters, followers, asks) commit nothing while waiting: a parked reporter would lose its child's answer and a parked ask would leave its session busy. `SessionHost.pendingWakers` excludes tasks pi-durable reports as blocked.
- A storage error fails the Harness. `SessionHost` reopens the store (after 0, 1, 5 s) and `SessionStartCoordinator.reattachDurable` moves active sessions onto it; if every reopen fails the host is abandoned and its sessions end `store_failed`. One recovery runs at a time; `SessionHost.failedWithStore` routes a re-attach that hits the failing Harness to the next recovery.
- A compromised directory lock is never recovered: another process may hold it. The host is sealed, the lost lock never released, and the store refused for the rest of the process, so Oppi never becomes a second writer. `ELOCKED` → `durable_store_locked`; any other lock error → `durable_store_lock_failed`; Oppi never empties a lock directory. A release token ignores compromise reports that arrive after release.

### MCP in durable sessions

- `durable-mcp.ts` reuses Pi's MCP loader, connections, and conversion (`pi-mcp-internals.ts`). Each attachment owns one `oppi.mcp/<sessionId>` extension. Registry snapshots outlive an uninstall, so its tools reach the session only through a cell `close()` empties: a stale snapshot holds no connection, conversation, or backend. The Harness default selection is pinned to base extensions, so `{ add }` never picks up another session's MCP.
- A project `.pi/mcp.json` loads only after `resolveManagedProjectTrust`. MCP tools replay after a crash only with `readOnlyHint` or `idempotentHint`. The first prompt waits up to 10 s for the servers it offers.
- Sandbox sessions use `sandboxMcpForWorkspace` (`sandbox-mcp.ts`): only owner-picked global servers load, HTTP servers connect only to Allowed Hosts, and stdio servers run in the workspace VM through `VmStdioTransport`, never a second VM.

### Durable extensions

- Bundled packages live in `server/extensions/durable/<name>/` (install order: file-tools, ask, working-words, background-jobs, sessions, project-context, sql-explorer, notify, live-voice, control). pi-durable's `CodingTools` and `codemode` are installed directly; `codemode`'s `CodemodeSandbox` caps each script at 256 MiB and admits at most 8 running scripts server-wide.
- `durable-extension-loader.ts` loads user-scope Pi packages only (project trust off, so project `.pi/extensions` never load) that declare `package.json` `"oppi": { "durable": { "entry", "runtimes" } }`, through a fresh jiti whose aliases point pi-durable, chord, pi-ai, typebox, and `oppi/durable` at the server's copies. A package loads whole or not at all; a name or tool a built-in uses is refused, as is anything `registry.install` would throw on, and a failed install rolls that package back. A broken built-in fails the first open and keeps its old code on reload; built-ins are never uninstalled.
- `oppiHost()` (`oppi/durable`) is bound once per process (`bindOppiHost`) in a non-writable `globalThis` slot; a second bind throws. It scopes every answer to the calling conversation's env: `sessions(env)` reaches only the caller's own children (`DurableThreads.forCaller`), `control(env)` exists only for the control conversation, and an env the server did not make gets nothing. The server reads a built-in only through its `contract.ts`, never its entry.
- Selection roles: `defaultExtensions`, `builtInsFor(runtime)`, `attachedBuiltIns(spawn, notifies)`, `controlExtensions`; `tests/durable-builtin-selection.test.ts` pins them. Reload (`POST /durable/extensions/reload`) replaces extensions in place by name, so running calls finish on old code.
- Disabling an extension (`experimental.durableExtensions.disabled`, written via `Storage.mutateConfig`) leaves it installed so pending tasks resolve, but selections leave it out; names stay reserved.
- Each conversation records its Session in the `oppi.session` document (`durable-session-doc.ts`); `oppiHost().sessionName(api, context)` reads it through the caller's own `api`. `auto-name` is a Pi package (`server/extensions/pi/auto-name`), never a built-in; `setUpAutoNamePackage` lists it disabled in Pi's `packages` once per data directory and lists nothing when the user links their own copy. The legacy `autoTitle` key migrates through `extractAutoTitle` after backing up `config.json`.
- The Pi Tools setting (`piDefaultTools`) governs Pi's tools as in classic; a sandbox reads it global-only because its project settings file is guest-writable. An attach appends newly enabled tools and keeps old ones, as Pi's `/reload`.

## Subagents

`oppi.sessions` (`server/extensions/durable/sessions/durable.ts`) gives durable sessions one `subagent` tool (`spawn`, `send`, `wait`, `stop`, `list`). Children are addressed by name through the `oppi.subagents` document; the Harness's ownership edge is the only record of who spawned whom, and `launch.parentSessionId` is its write-once copy (clients build threads from it). No messages between sessions are stored.

- `spawn` creates and configures the child conversation in one commit. Every message to a child is delivered by a conversation-owned reporter task (`oppi.session-reporter`) keyed by the tool task id, so a rerun creates no second one; `Child.reported` keeps each answer reported once. With `wait: true` the spawning task owns the child and Stop reaches it; otherwise a background anchor owns it.
- `wait` never returns a stale answer: it first waits for undelivered messages, then until each child is idle with no pending wakers; a child whose only wakers are its own running background jobs counts as finished, with a note. Its final read and the withdrawal of any report a reporter already decided happen in one commit, so the parent reads each answer once. Waits run in-process inside the task phase because pi-durable joins only `allSettled`/`failFast`, which would hold an early answer until the slowest job ends.
- Reserved request ids (`durable-request-ids.ts`): `oppi-spawn:`, `oppi-report:<childConversationId>:<answerEntryId>`, `oppi-report:<reporterTaskId>`, `oppi-send:`.
- **Worktrees:** `DurableThreads.planWorktree` checks host runtime, a git workspace, and ownership, and holds a `"new"` branch until provisioning settles; a `"new"` spawn never adopts a worktree. Both kinds go through `ensureWorkspaceWorktree` like the HTTP route. The server never removes a child's worktree; a child whose worktree disappears fails closed (`resolveSdkSessionCwdAsync`, `ensureManagedWorktreeBinding`).
- **Tools:** `narrowTools` always intersects with the spawning session's tools; `tools`/`readOnly` become an exact policy an attach cannot widen; `excludeTools` only adds exclusions.
- **Nesting:** `childDelegationGrant` (`agent-launch-service.ts`) is the one rule: a top-level session may spawn; a child only with `allowNestedDelegation`; sandbox children stay in the sandbox and never get the grant. Host envs carry `OPPI_CALLER_SESSION_ID`, so `oppi session create` from a child is parented and refused without the grant.
- **Agents:** `resolveDurableAgent` (`durable-agent.ts`) is the one resolver from a saved Agent to pi-durable's `AgentChange` plus the `oppi.agent` document; Extensions without a durable entry are named in `extensions.skipped` and become a `Session.warnings` entry. After launch the definition is never read again. A conversation without `oppi.agent` never spawns.
- **Child sessions:** `DurableThreads` materializes each child's Session once (key `durable-thread:<conversationId>`; clients cannot use that prefix) with `autoStop`. Every submission goes through `DurableSessionsHost.activate` (`SessionManager.withIncomingWork`), and the auto-stop recheck runs under the session lock with no await, so incoming work and a stop never cross. A child that cannot attach is reported to the parent rather than faulting the reporter. A full Stop of the parent aborts its reporters (`abortSessionReporters`); children and jobs keep running.

## Oppi Control

- A durable Oppi Control session is a workspace-less row with `serverDurable.role: "control"` and its own store, on every server. `POST /control-sessions` creates one per Edit with Oppi request; the standing control conversation (one per data directory, launch key `control-conversation`) comes from `POST /control-conversation` (`ControlConversationService`). Both select the exact `controlConversationExtensions` array, re-asserted on every attach, run in the owner-only `$OPPI_DATA_DIR/control-conversation/cwd`, and load no AGENTS files, Skills, MCP, or packages. They are listed only with control sessions, never in a workspace catalog or count.
- `oppi.control` registers `oppi({ argv })` and typed tools that only build argv. `DurableControlCli` (`durable-control-cli.ts`, reached only through `oppiHost().control(env)`) refuses file flags, `@-`, `config set`, `--config-file`, the `control` family, `status` (synchronous shell-out on the event loop), and inline `--idempotency-key=`/`--request-id=`/`--turn-id=` forms. It replaces every replay key with `<tool call task id>:<argv hash>`.
- Every write waits for a confirm card (`requestUI` select); a read tool's non-GET throws. Cards are answered only as `extension_ui_response` by owner or paired-device credentials; no CLI verb answers one, and a new verb that would must be refused by `DurableControlCli`. "Yes to all" covers one script only. A card shows the whole body; over 6000 characters is refused (`body_too_large`). Each card's request is stored before asking (`oppi-card:<slot>`), and a rerun that builds a different request fails `card_changed`. The cards gate only `oppi.control`'s tools: `bash` is unrestricted and the cards guard against the model, not other local processes holding the owner token.
- Replay is exactly-once only for the keyed commands (`agent create`, `session create`, `schedule create`, `schedule run`, `session send`). Residual risks: `agent update`/`archive` have no key (a crash reports a false failure; pass `expectedVersion`, or an `append` patch applies twice); unkeyed `oppi(...)` writes can apply twice; a transport error after the write is memoized as failure; `config show|get|validate` may spin up to ~5 s on the event loop; replay keys are not scoped to one store.

## Durable gaps and unsupported operations

- `DurableNotSupportedError` (`server_durable_not_supported`) for `sessionTree`/`navigateTree` (navigating would fork, drop later turns, and strand background work; fork-from-a-message is the way back), `abortBash`, `appendAssistantMessage`, and classic queued-turn replacement. Incognito and Extension selections without a durable entry are rejected.
- Fork uses `conversation.fork(entryId)` at the entry before the chosen user message; `SessionHost.forkConversation` decides what a fork carries, so it launches as its source. A durable source never falls back to a Pi JSONL fork. Share exports through a temporary JSONL (`durable-export.ts`).
- Run-policy setters write the global `SettingsManager`, not per session.
- `abortRetry` marks the generation task only while its checkpoint is still in a retry backoff, via `Tx.setTask` (fails loudly if pi-durable drops it). After an aborted run, queued inputs wait for the next message. After a failed run, `DurableAgentController.continueAfterFailedRun` admits a hidden `oppi.continue` write after the failure card so queued inputs follow it, and the session settles once.

## Saved Agents and schedules

- `AgentLaunchService` owns idempotency, launch recovery, target constraints, and prompt dispatch. Incompatible targets and unavailable Skills or Extensions fail closed as typed configuration failures; allowed tool names with no matching tool are dropped and surfaced in `session.warnings`. Pre-start failures return a non-retryable 422 with no session; post-start failures keep one `error` session. Focused streams close with policy violation instead of reconnecting.
- A launch left `launching` after a crash is never redispatched, because persistence cannot tell a crash before send from one after Pi accepted the turn.
- Classic declared Pi Control rows are no longer created but still list, resume, and run on the SDK path with `buildControlSystemPrompt` as `systemPromptOverride`, `noContextFiles`, `noSkills`, and a tool allowlist of `read`, `bash`, `edit`, `write`, `ask`.
- Agent and schedule validators reject unexpected fields and empty updates. There is no `oppi skill` CLI or Skill PUT; catalog editability is presentation, not authorization. Theme routes are read-only.
- `AgentScheduleRunner` claims due runs with a lease and dispatches through the manual-run hooks. An `at` schedule archives itself in the transaction that completes its slot; restoring never reruns it because the run holds the idempotency key.

## Terminal mirror runtime

`PiTuiMirrorRuntime` owns `/mirror/v1/bridge` and implements the same `AgentRuntimeTransport` as the managed runtime, projecting through the shared pipeline. If the bridge disconnects, the session stays `"pi-tui"` unless the app explicitly resumes it as managed.
