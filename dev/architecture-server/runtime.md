# Oppi server architecture: Session runtime

Part of [Oppi server architecture](../architecture-server.md). Runtime ownership, the managed SDK runtime, saved Agents and schedules, and the terminal mirror.

## Session runtime ownership

`SessionRuntimes` is the server facade for runtime-owned operations. It dispatches by persisted `Session.runtime`:

- `"oppi"` routes to managed `SessionManager` and the in-process Pi SDK backend.
- `"pi-tui"` routes to `PiTuiMirrorRuntime` and the terminal bridge.

The facade handles common calls such as prompt, steer, follow-up, abort, stop, queue state, pending UI, event catch-up, snapshots, and full tool-output paths. Route and stream code should prefer `SessionRuntimes` when the command applies to either runtime owner.

A stopped, disconnected mirror session with a canonical session file can be promoted to `"oppi"` on resume or focused-stream open. A connected or stale terminal-owned session stays terminal-owned. A terminal bridge can take over an existing `"oppi"` session only after explicit terminal confirmation; if that session is active, the server stops the managed runtime before switching ownership.

## Managed SDK runtime

`SessionManager` is the managed runtime facade. It keeps active sessions in memory and delegates most behavior to coordinators from `session-coordinators.ts`:

- `SessionStartCoordinator` creates SDK-backed active sessions.
- `SessionActivationCoordinator` handles start/resume idempotence.
- `SessionInputCoordinator` handles prompt, steer, follow-up, attachment validation, and first-message capture.
- `SessionMessageQueueCoordinator` owns steering/follow-up queue state.
- `SessionCommandCoordinator` forwards SDK commands and applies SDK snapshots.
- `SessionAgentEventCoordinator` translates Pi events into server messages.
- `SessionBroadcaster` assigns per-session sequence numbers and supports focused-session catch-up.
- `SessionStopFlowCoordinator` and `SessionStopCoordinator` own abort/stop behavior.
- `SessionLifecycleCoordinator` handles idle timers and session end cleanup.

`sdk-backend.ts` wraps Pi's `AgentSession`. It resolves workspace cwd, configures sandbox tools when requested, binds extensions through `SdkUiBridge`, injects session attachment helpers, forwards SDK commands, and emits Pi events back into the session projection pipeline. Declared control sessions use an owner-only, non-symlink `$OPPI_DATA_DIR/control-sessions/cwd` as the real Pi SessionManager cwd. They otherwise use ordinary Pi global configuration and resources. `Pi Control` remains display metadata only and must not be persisted as SessionManager cwd, or Pi JSONLs land under the server process working directory and leak into workspace importable-local discovery. Sandboxes still keep their guest/display cwd split with a host existence override. `session-work-root.ts` is the one owner of "which host directory belongs to this session" (workspace mount or worktree, declared control cwd, control-conversation cwd): session start and attachment writes ask for creation, while reads and cleanup never create directories. Routes and services call it instead of rebuilding paths.

The managed pipeline uses the `AgentBackend` interface in `server/src/agent-backend.ts` for commands, queue authority, lifecycle transactions, and runtime snapshots. `SdkBackend` implements this seam and keeps the live Pi `AgentSession` inside the adapter. Both managed backends reuse the sandbox VM owner exposed by `SdkBackend.ensureSandboxWorkspaceVm()`. `GondolinManager` derives a VM's read-only Skill mounts itself at boot, one per `.pi/skills` entry of the workspace (owner-trusted: the workspace shadow hides `.pi` from the guest), and records them as `GondolinVm.skillMounts`; callers pass none, and the mounts are not part of the VM fingerprint, so every session on a live VM sees the same mounts and a new `.pi/skills` entry waits for the next boot. A sandbox session presents only Skills the VM can serve, discovered through the VM by one function, `loadSandboxSkills` (`durable-project-resources.ts`, over a `GondolinExecutionEnv`; below). Classic ensures the VM before its `DefaultResourceLoader`, turns off Pi's host Skill discovery (`noSkills`, no additional paths, extension-provided Skill paths dropped in `extendResources`, and `keepSandboxSkillDiscoveryOffHost`: Pi's package manager still walks `.agents/skills` from its cwd on every reload whatever `noSkills` says, synchronously and without a cycle guard, so its private `addAutoDiscoveredResources` runs from `/`; session creation fails if Pi no longer has that shape) and host context-file read, and before each load takes the VM's Skills (presented through `skillsOverride`; a selection the VM cannot serve fails `agent_skills_unavailable` at launch, or blocks model turns after a reload) and the guest root's context file (`readVmTextFileWithin`, the same shadowed, jailed provider and 1 MiB cap as durable). Pi's own `/skill:` expansion reads the guest path on the host, so a classic sandbox registers an inline `input` handler (`createSandboxSkillCommandExtension`) that expands it first through `GondolinExecutionEnv.readSkillFile`, the bounded read durable's `/skill:` uses. A VM refusal is caught there and returned as `handled`, not thrown: `emitInput` would otherwise swallow the throw and `_expandSkillCommand` would `readFileSync` the guest path on the host. Session creation selects the SDK unless the session is enrolled in the experimental server-durable backend.

## Server durable (experimental)

`oppi config set experimental.serverDurable true` makes durable sessions available after a server restart; it never enrolls a session by itself. A session runs on `DurableBackend` only when its create request asks for `engine: "durable"` (`POST /workspaces/:id/sessions`, `oppi session create --engine durable`). An omitted engine, or `"classic"`, is the SDK backend; quick actions, control sessions, imports, forks of classic sessions, and scheduled or Quick Session launches without the field stay classic. Saved Agents start durable sessions the same way: `POST /agents/:id/sessions` (`oppi session create --agent <x> --engine durable`) and new-session schedule actions (`engine: "durable"`, `oppi schedule create --engine durable`) take the field; the Apple Quick Session still runs a saved-Agent launch Classic. Asking for durable while the flag is off fails with HTTP 409 and no session; an unknown engine is HTTP 400. A durable request the backend would refuse at start (incognito; `durableUnsupportedFeature` is the one list both use) is HTTP 400 before any session row exists. A durable saved-Agent launch skips `AgentLaunchService`'s classic Extension preflight: the session starts without the selected Extensions that have no durable entry (see `resolveDurableExtensionSelection` below). An idempotent replay that asks for the other engine than the stored session is HTTP 409. `SessionManager.durableSessionsAvailable()` reads the startup flag, and `GET /server/info` advertises `capabilities.durableSessions: { version: 1 }` only while it is on. `SessionSummary.engine` is `"durable"` for durable sessions and omitted for classic ones; full `Session` payloads mark the durable engine with `serverDurable`. `session_state_sessions` stores the binding as `durable_store_id`, `durable_conversation_id`, and `durable_role`, indexed on `(durable_store_id, durable_conversation_id)` so a store's conversation finds its session without a scan. Child sessions that `oppi.sessions` spawns are created bound to their conversation, so they are durable without a request field. The flag is absent by default. Existing SDK and terminal sessions do not change. A bound durable conversation cannot switch between host and sandbox execution, or move to another sandbox workspace.

`DurableHarness` is the process-owned durable runtime: the server's `ModelRuntime` (the same `auth.json` and `models.json` runtime that already carries global provider-extension registrations, including Anthropic OMP), the shared registry and package-extension reload, global `SettingsManager` run policy, and the base and control extension lists. Production open fails if that shared runtime was not bound. A private runtime is only for tests and callers that have not discovered extensions. Each durable session tree has a `SessionHost` at `$OPPI_DATA_DIR/durable/sessions/<rootSessionId>/` (`meta.json` plus `session.sqlite`, directory locked with proper-lockfile while open). The host owns that store's Harness, resume gate, sandbox envs, MCP connections, and live streams, and closes when no session of the store is attached, no stream is subscribed, and the task graph has no live tasks. Conversation ids are per store; `Session.serverDurable.storeId` is the root session id (server-internal). A row without `storeId` cannot open as durable. Sub-agent children and forks are conversations in the root's store. The control conversation has its own store; the row is created when the server starts. CodingTools (read/write/edit/bash) and a Node execution environment still apply per host cwd. Sandbox conversations persist their execution boundary in `oppi.execution-runtime` and attach a `GondolinExecutionEnv` before scheduling resumes. An unattached sandbox fails closed instead of falling back to host execution. It reuses the manager's per-workspace VM, keeps file tools inside `/workspace/<slug>`, and never forwards the host shell environment. Guest ls/find/grep use the existing sandbox operations; a sandbox-only read wrapper returns image content. Every shell/search execution uses `setsid` and kills its guest process group on cancellation or timeout. A pre-exec stream handshake captures the guest pgid and process starttime in host memory before launch; cancellation waits for the identity-checked group kill and reports failures. Guest root can replace `/bin/sh` or `/usr/bin/setsid` on the VM's writable root and forge the next handshake; that root can already signal any guest pid. A descendant that calls `setsid` leaves the captured process group: Stop kills the original group and confirms while the new session keeps running. Environment cleanup cancels its calls but never stops the shared VM. The shared session-status path holds the VM while a runtime is attached and allows idle teardown after Stop or error. Session-local model and thinking choices persist through `configure()`. `Session.serverDurable` records enrollment, `storeId`, and the conversation ID before the first submission. Apple `clientTurnId` becomes Durable `requestId`; command correlation IDs do not. Native reporters reserve request ID prefixes through `durable-request-ids.ts`; client turn IDs using those prefixes are rejected before admission.

`SessionHost` also owns the session services of its conversations, built from the Harness, the conversation, and the host only (no `Session`, no event callback, no classic frames), cached per conversation for the opened Harness and dropped when it closes (a lookup that outlives a close caches nothing). `host.controller(conversationId)` is the one `DurableAgentController` (`durable-agent-controller.ts`): `prompt` (with `steer` and `followUp`) owns the request-id dedupe and content fingerprint (`oppi.request-content`), the per-conversation admission chain, and the input failure card; then `cancelQueued`, `queue`, `abort`, `abortRetry`, `compact`, `waitForPrompt`, and `fork`. `host.models(conversationId)` is `DurableModels` (`durable-models.ts`, over one `ModelRegistry` per host): `current`, `available`, `select`, `selectThinking`, `cycleModel`, `cycleThinking`. `host.transcript(conversationId, …)` attaches the conversation stream. `DurableBackend` is the classic-event facade the session socket still reaches through `AgentBackend`: its input, queue, run, and model methods delegate to those services, and it keeps lifecycle permits, Skill expansion, `mcp.beforePrompt`, the `queue_update`/`prompt_error`/`queue_item_started` events, and the queue version. Every client input goes through that controller, so a request id is admitted once whichever socket path sends it, and a changed content under a used request id is rejected. `subagent wait` uses only its `waitForPrompt` (`DurableThreads.waitForIdle`). The `subagent` reporters, and `wait` waiting on a message a reporter has not delivered yet, submit to the child conversation directly under reserved request ids no client can send; pi-durable's admission returns the existing submission for a used request id, which makes those one submission. The iOS client attaches to the conversation stream and no longer gets the timeline events it restates, but still reads the run boundaries, session state, errors, notices, and command results the facade emits, and the Mac app reads every classic event; moving both to `Transcript` deletes the facade, the event adapter, and the event projection.

Committed events pass through `durable-event-adapter.ts` to the existing Pi event projection and Oppi sequence ring. Separately, a focused socket that sends `attach` also receives the experimental conversation stream (`durable-conversation-stream.ts`, `capabilities.conversationStream`): a snapshot of the conversation's active entries and client-visible documents, then coalesced entry and Chord-op updates driven by Harness commit publications, with entry-id resume and no sequence numbers. It reads that session's store Harness directly and does not depend on the backend being attached; an attached socket stops getting the classic events the stream restates, while sockets that do not attach, and classic and mirror sessions, are unchanged. See [Durable conversation stream](durable-conversation-stream.md). State and queue reads use `pi.agent`, `pi.live`, `pi.usage`, and `pi.inbox`. Startup reopens stores of sessions in the resume queue. Opening a store aborts leftover tasks of conversations whose session rows are neither active nor queued for resume, including background tasks, and withdraws their queued inputs while each host's scheduler is paused, then attaches resumable conversations and calls `resume()`. Crash healing queues live idle sessions too, so their conversation-owned background work can resume. It rechecks the restart queue before each attach and after cancellation awaits so an explicit stop or deleted workspace wins. Each host's scheduling gate is held from open through startup resolution for that store. Stops use paused task/submission cancellation while it is held; prompts and compaction fail with a retryable startup error instead of waiting while holding admission permits. Failed input admission leaves restart intent intact. Native inbox reconciliation reserves rich queue metadata before submission, then commits or discards it with admission so broadcasts preserve attachment references without duplicate chips. Both crash recovery and graceful restart continue the original submission without a restart continuation prompt. Explicit stops abort unfinished work. Shutdown detaches conversations recorded for restart without aborting them, and aborts only those that must stay stopped before closing storage. Unsafe tools interrupted by a crash report interruption; they do not automatically rerun their side effects.

Live assistant text and thinking are projected from Durable partials as append-only `text_delta` / `thinking_delta` while the new partial extends the text already sent. A non-prefix rewrite (an OpenAI Responses done-item replacement, or a `text_end` / `thinking_end` block that is not an extension of the streamed prefix) sends the same delta plus `replace: true`. The delta is the current partial for that content index. New clients write that partial into the existing row for the index, including a rewrite of an earlier block while a later block is open, and do not close the other modality. Older clients ignore `replace` and append the delta, which is the previous behavior, so they are no worse until `message_end`. Trace history still reads committed entries. The append-only path is unchanged when the partial is a prefix.

A durable input that settles `unanswered` for a reason other than `aborted` or `withdrawn`, and a faulted or orphaned task that is not compaction and not the generation whose inputs already settled, is recorded as a display-only transcript card (`data.card`, accent `error`) with no model messages. The write uses a reserved `oppi-failure:` request id, so a retry is the same card. The input card commit is queued before any await, and the request-id and visible-text checks run inside that commit, so a prompt sent immediately after the failure cannot land ahead of the card. Attach reconciles a crash between settlement and that write by paging unanswered inputs through the storage `SessionHost.open` retained (`Storage.scanSubmissions`), not a second connection and not pi-durable's private tables. A failed scan fails the attach. Terminal tasks already examined are not scanned again: conversation document `oppi.failure-cards` records the high-water task id and any still-open task ids at or below it, written in the same commit as new cards, and attach examines only newer tasks plus those open ids. Missing task cards are existence-checked in that one commit. History (full trace, page, and outline) shows the card at the write position. An assistant entry with `stopReason: "error"` does not carry `errorMessage` into the trace, so the card is the history row unless that same text is already visible assistant text. The live `error` has the card's text: `DurableBackend` emits one `prompt_error` per failed run from the unanswered `submission` event or the `task_failed` event, whether or not a card was written, so live, reconnect, and restart show the same reason. Within a run it skips text already shown live: an assistant `stopReason: "error"` message (the classic protocol's error row), the `Compaction failed: <error>` of a failed blocking compaction on its compaction row, or another input of the same run. The set resets with the batch that ends the run (`run_end`; settlement commits with it). Inputs from any source get their card from the backend's `submission` events, not only prompts sent through the controller; the failure card does not also emit a notice.

Each Harness opens with an `onReport` that logs `durable_store.report`: the store id, what pi-durable's `ReportInfo` says the report is about (`type`; for a task its `taskId`, `taskKind`, and `conversationId`, which `(durable_store_id, durable_conversation_id)` binds to one Session; the `extension` whose code failed; the host `callback`; the typed `reason`), and the redacted message and cause. pi-durable sends there the failures that do not fail the calling operation (a throwing hook, extension, or commit listener; a faulted or outdated task; a failed task migration; the storage error that fails the Harness, as `session_failed`), and drops them when no handler is set.

Opening a store migrates its SQLite file to pi-durable's schema version 2 (pi-durable 1.4.0), which rebuilds the task table; pi-durable 1.3.0 cannot open a migrated store, so a server downgraded past that pin cannot open its durable sessions. Waits are durable sleeps: a task in a retry or compaction backoff, or before a deferred-response poll, commits `sleeping` and holds no invocation, a sleeping task keeps its store open like any live task, and a restart resumes it at its checkpoint when it is due. pi-durable 1.4.0's crash-loop guard is off: `harnessSettings` sets `restartLimit: Infinity`, which keeps 1.3.0's behavior, so a task cut off by a crash runs again on every restart however often that happens. The guard parks a task cut off 5 times in a row without committing a new state, and Oppi's long in-process waits commit nothing while they wait: a reporter delivering a message to its child (`submission.wait`), a follower waiting on the child, and an ask or other dialog card waiting for its answer. A parked reporter would lose its child's answer, and a parked ask would leave its session busy until Stop. A task can still be blocked for want of a definition (its extension's package removed, or a stored version newer than the installed one); such a task never ends by itself, so `SessionHost.pendingWakers` leaves out every task pi-durable inspects as blocked, and a blocked reporter or job does not hold its session's idle timeout.

pi-durable fails a Harness on any storage error: every later call rejects with `SessionFailed`, and the Harness closes itself and its storage. `SessionHost` watches `harness.closed`; on a failure it did not cause, it drops the services, MCP connections, task-graph watch, and directory lock bound to that Harness and reopens the store (attempts after 0, 1, and 5 s). Commits are atomic, so the reopened Harness resumes from what was committed. Open transcript streams re-attach after the last entry they sent. `DurableHarness.onHostRecovered` then lets `SessionManager` move each active session of the tree onto the reopened Harness (`SessionStartCoordinator.reattachDurable`: a new `DurableBackend` under the workspace lock, without status changes) and post a notice. When every reopen fails, the host is abandoned for good: it releases its sandbox envs and streams, the runtime forgets it, its `open()` rejects with the error (so a waiter cannot reopen a host the runtime no longer tracks), and those sessions end with `store_failed`; the next `openHost` builds a fresh host. A session whose own re-attach throws ends alone, with its sandbox env force-released, unless the store failed again meanwhile (`SessionHost.failedWithStore`: `SessionFailed`, a recovery under way, or the current Harness began closing on its own, seen through `subscribeClose` because the call that hit the storage error gets the raw error before `closed` settles): then the next recovery re-attaches or ends it. One recovery runs at a time; a failure of a Harness that a recovery attempt dropped is ignored, and an unexpected error inside recovery abandons the host rather than leaving it recovering. Shutdown during the retries seals the host (sandbox envs and streams released) without ending sessions. `open()` and `close()` wait for a recovery in progress. Recovery starts only once the failed Harness's `closed` settles, which can be after the failing call has already rejected; an `open()` in that window still gets the failing Harness, whose calls reject with `SessionFailed` (`failedWithStore` sends a re-attach that hits it to the next recovery).

Host durable sessions load Pi's MCP servers through `durable-mcp.ts`, which reuses Pi's MCP config loader, connections, credentials, naming, and result conversion from `pi-mcp-internals.ts` and replaces only the classic glue. Each attachment owns one registry extension, `oppi.mcp/<sessionId>`, that `DurableHarness` installs, reinstalls in place when a server's tool list changes, and uninstalls on Stop or shutdown. The Harness default extension selection is pinned to the base extensions, so an `{ add }` selection never picks up another session's MCP extension. A project `.pi/mcp.json` loads only after `resolveManagedProjectTrust` through the startup UI bridge, as for SDK sessions. `direct` tools are appended to the conversation's explicit tool list; `codemode` (Pi's `codemode` built-in does not exist on durable) and `deferred` tools are reached through a durable `tool_search` that returns `control.addTools`, so loaded tools persist in `pi.agent`. The launch tool policy follows Pi's (`AgentSession._isAllowedTool`/`_isActivatable`): allow and exclude entries match names or `*` patterns, and an allow list that names no `mcp__` entry keeps the MCP tools `tool_search` can load (not `direct` ones). An allow list naming `codemode` also permits `tool_search`, durable's way to what classic reaches through codemode. The first prompt waits up to 10 s for servers whose tools it offers, and attaching a busy conversation waits for startup connections before resume so recovered calls find their tools. MCP tools replay after a crash only with `readOnlyHint` or `idempotentHint`. Startup problems are one `notify` warning; signed-in servers reconnect before the next prompt. Sandbox durable sessions use the same module with `sandboxMcpForWorkspace` from `sandbox-mcp.ts`, the policy classic sandbox sessions hand to Pi's MCP extension: only the global servers the owner picked load (never the project `.pi/mcp.json` or extension-registered servers), HTTP servers connect from the host only to Allowed Hosts, stdio servers run in the attachment's workspace VM through `VmStdioTransport` (it connects after `bind` ensures that VM, and never starts a second one), there is no codemode, and server logs go to `sandbox-mcp-logs/<workspaceId>.log` in the data directory.

Durable sessions install native `ask`, `working-words`, and `background-jobs` extensions from the bundled packages `server/extensions/durable/<name>/` (real directories whose files are symlinks to the files of `pi-extensions/<name>/`), next to Oppi's other built-ins there: `oppi.sandbox-tools`, `oppi.sessions`, `project-context`, and `oppi.control`. A committed `oppi.extension-ui` conversation document supplies pending dialogs and persistent UI through the existing extension UI projection. Pending asks survive process restart and accept the first committed answer; Abort and Stop cancel them. Background shell jobs belong to the conversation and survive ordinary Stop. Bash waits up to 15 seconds before returning a background-job notice; a trailing `&` backgrounds immediately. Jobs run in the conversation's host or sandbox execution environment. Restart reports an interrupted execution without rerunning the shell. Each job persists a `background-job:<id>` follow-up receipt. Queued receipts remain undelivered; withdrawn or mismatched receipts advance to a persisted `background-job:<id>:<n>` ID. Delivery requires matching content and a placed or done receipt, then settles the job runner, which retires its task-scoped output document and that document's stored revisions atomically. Results are not combined into classic-style batches, and widgets show final output only. See [Durable extension UI](durable-extension-ui.md) for the document convention, loading, and proof commands.

Durable sessions also select extensions loaded from Pi packages. `durable-extension-loader.ts` resolves the enabled user-scope packages with Pi's `DefaultPackageManager` (cwd `homedir()`, project trust off, so project `.pi/extensions` never load), takes each package's durable entry from `package.json` `"oppi": { "durable": { "entry": "./…", "runtimes": ["host", "sandbox"] } }` (`readDurableManifest`: strict, `runtimes` defaults to host, a `.js` entry finds its `.ts` source; no manifest means no durable entry, and single-file extensions have none), and imports it with a fresh jiti instance (`moduleCache: false`, `tryNative: false`) whose aliases point `@earendil-works/pi-durable`, `chord`, `pi-ai`, `typebox` and `oppi/durable` (`durable-extension-api.ts`) at the server's copies; node_modules load natively, so they are the same module instances the Harness uses. The default export is a plain pi-durable `Extension` or an array of them; a package loads whole or not at all. Oppi's bundled packages (`bundledDurableExtensionPackages`, `server/extensions/durable/<name>/`, in install order: sandbox-tools, ask, working-words, background-jobs, sessions, project-context, sql-explorer, notify, control) load through the same function first: a broken one fails the runtime at open and keeps its previous code on reload, and a built-in is never uninstalled. Only pi-durable's `CodingTools` (first) and the control conversation's `codemode` (after the built-ins; it owns the server's `CodemodeSandbox`) are installed directly. Built-ins that need server internals get them from `oppiHost()` in `oppi/durable`, which the first `DurableHarness` of the process binds (`bindOppiHost`) before any package loads. The binding sits in one process-wide `globalThis` slot because each entry evaluates its own copy of `oppi/durable`; the slot is defined non-writable and non-configurable, and a second `bindOppiHost` throws, so a package cannot replace the host the built-ins use. One host object serves every runtime of the process: the env factory and `bindSandboxEnv` record which session host and conversation each execution env runs (`conversationOfEnv`), and the host scopes each answer to the conversation of a tool call's `api.env`. `sessions(env)` is `DurableThreads.forCaller`, which takes only Sessions bound to conversations whose owner is the calling conversation (its own children, as `subagent` reaches them by name) for `waitForIdle`, `activate`, `pendingWakers`, and `materialize`, and refuses any other Session of any store. `control(env)` is `DurableControlCli.forConversation`, undefined unless that conversation of that store is bound to the control Session (conversation ids are per store, so both are compared), and `run` refuses a conversation that has no control Session before it parses argv. An env the server did not make gets neither. `notify(env)` is the push send for the Session bound to that conversation (`SessionPushNotifier.notify`), undefined for an env the server did not make. `sandbox` is `durable-sandbox-host.ts`'s Gondolin ls/find/grep and image read. What the server reads of a built-in lives in its `contract.ts` (or `oppi/durable` for host types and `SESSION_REPORTER_TASK`), never in an entry, which only the loader can import. Selection reads the loaded built-ins by role: `defaultExtensions` (the Harness default: CodingTools and every built-in but control), `builtInsFor(runtime)` (a new session's start: those whose manifest runtimes allow it, so sandbox tools only in sandboxes), `attachedBuiltIns(spawn, notifies)` (a bound conversation's `{ add }` on attach: those every runtime allows, `oppi.sessions` only with spawn, `oppi.notify` only while `offersNotify`; each left out is also in the edit's `remove`, since the Harness default includes it), and `controlExtensions` (`ask`, `working-words`, `oppi.control`, `codemode`). `tests/durable-builtin-selection.test.ts` pins the result per runtime. A user package's name or tool name that a built-in (or CodingTools, or `codemode`) already uses is refused; a package whose extensions are all built-ins is skipped, which covers the user's symlinks to `pi-extensions/ask` and `background-jobs`. The loader also refuses what pi-durable's `registry.install` would throw on (a task name another installed extension or pi-durable holds, or one taken earlier in the load; two tools or two sections of one name; a section key outside `^[a-z][a-z0-9_-]*$`, or `instructions`), so these are that package's load error. Installs then run package by package (`installPackages`): should one still throw, the package's extensions installed in that load are put back to their previous code (or uninstalled) and it is a load error too, so one bad user package never stops a load halfway or fails the runtime, and the registry and `packageExtensions` stay the same set; only a broken built-in fails the first open. `DurableHarness.ensureShared` loads them into its registry before any `Harness.open`, so pending tasks find their definitions, and again on `reloadExtensions()` (`POST /durable/extensions/reload`, `oppi extensions reload`), one load at a time. A reload installs every loaded extension under its name, replacing the old object in place (pi-durable resolves extensions by name at each task phase, so running calls finish on the old code); a package that failed to load keeps its previous code; a Pi package that is gone is uninstalled. The report marks bundled entries `builtIn: true`. The owner turns a loaded durable extension, built-in or from a package, off and on by name (`GET /durable/extensions`, `PUT /durable/extensions/{name}/enabled`, `oppi extensions list|enable|disable`), stored as `experimental.durableExtensions.disabled` in the server config and read at each use through `DurableHarness.isExtensionEnabled`. A disabled extension stays installed, so its pending tasks still resolve, but `defaultExtensions` (a getter in the Harness settings, so `{ add, remove }` selections follow without reopening), `builtInsFor`, `attachedBuiltIns`, `packageExtensionsFor`, and `resolveDurableAgent` leave it out: new sessions and spawns start without it, a bound session drops it at its next attach (a sandbox session drops `oppi.sandbox-tools` at its next resolve, since only the default selection carries it), and a saved Agent that selects it gets it in `extensions.skipped` and keeps that launch-time selection after it is enabled again. `working-words` has no tools, only a ticker task that runs from the registry, so `DurableBackend.bind` does not start the ticker while it is disabled. The route writes through `Storage.mutateConfig`, so it never writes back a stale copy of other `experimental` keys. Package names stay reserved for every built-in, enabled or not. The control conversation keeps its exact selection. `DurableBackend.bind` adds `packageExtensionsFor(runtime)` and their tools to a new conversation's exact selection and to a bound conversation's `{ add }` edit and tool list on every attach; the control conversation gets none. A newly added extension reaches an attached session at its next attach.

Durable sessions manage child sessions with one `subagent` tool from the native `oppi.sessions` extension (`server/extensions/durable/sessions/durable.ts`), shaped like pi-durable's example 23: `spawn`, `send`, `wait`, `stop`, and `list`, with children addressed by name through the conversation's `oppi.subagents` document (name to child conversation and Session, plus which spawn call made which, so a rerun finds its child). Ownership is the Harness's, and it is the only record of who spawned whom. `spawn` resolves the child through the host (`oppiHost().sessions(env)`, which is `DurableThreads.forCaller` for the calling conversation; `resolveAgent`), then creates the child conversation and configures it in one commit (`apply`: `configure` with the resolved `AgentChange`, the parent's `DurableRuntime`, and the child's `oppi.agent` document), then binds its Session. With `wait: true` the child is owned by the spawning tool task, so the parent stays busy until the child is idle and Stop reaches it through the cascade, and the call returns the child's answer. By default a background anchor task owns it, and Stop does not reach it. Every message to a child, the spawn's task and each `send` (a steer, or a follow-up after its answer with `followUp: true`), is delivered by its own background, conversation-owned reporter task (`oppi.session-reporter`) in the parent, created in the tool's commit and keyed by the tool task id (`Child.reporter` for the spawn, `oppi.subagents` `reporters` for a send), so a rerun creates no second one. The reporter submits the message to the child, waits for that submission's settlement, and posts the answer to the parent as a `whenBusy: "followUp"` input. `Child.reported` lists the answers already reported: several messages that end in one answer (a steer that joins the task's run) report it once, and the commit that decides a report records its answer. `wait` first lets the earlier `subagent` calls of its own tool round finish (a `send` in the same answer), then waits for the answer to every message to the child whose reporter has not delivered it yet (it submits the reporter's own draft, whose request id makes it the reporter's submission; a reporter Stop aborted is skipped), so it never returns the previous answer of a child that has not started on the message. Then it waits until every named child is idle (or failed), and only then, in one commit just before it returns, reads each idle child's latest answer and records it as reported, so no reporter decides to report it afterwards. When a reporter already decided to, the same commit withdraws that report: the parent is busy inside the `wait` call, so a submitted report is still queued and is settled `withdrawn` and dropped from the inbox (as `Harness.abortSubmission` does); a report a live reporter decided but has not submitted has its request id taken by a record already settled `withdrawn`, so the reporter's submit returns that record. An answer an earlier `wait` already returned gets no such record. The result lists each child's answer, and a failed child's error next to the others. The parent reads each answer once: as the `wait` result, or as the report when `wait` is aborted before that commit, for one child or several. A Stop of the parent itself withdraws its queued input, a queued report included, as Esc does in pi-durable's example. After its report, a reporter follows the child, so answers no parent message caused also come back, such as the answer a child gives when its own background job's receipt wakes it. One reporter per child follows (`Child.follower`). While the child has pending wakers (`DurableSessionsHost.pendingWakers`, the same set as `SessionHost.hasPendingWake`: its undelivered background jobs and its own reporters, never tickers such as the pill or working words, which do not end), it waits in its `follow` phase until a waker ends or the child's `pi.live` changes, waits for the child to be idle, and reports the newest final answer after its last one that is not yet reported. It ends once the child is idle with no pending wakers, so it never holds the parent's idle timeout or the store longer than the child's own work. A child commit between reading the wakers and deciding makes it decide again, so a job started in that gap is not missed. The waits are in-process inside the phase rather than a durable `waiting` state: pi-durable joins only on `allSettled` or `failFast`, so a durable wait on several jobs would hold an early job's answer until the slowest ended. The phase reruns after a restart, and request ids and `reported` keep each report single. A reporter whose `report` checkpoint has no `after` ends after its report. `stop` aborts a child's current work and keeps it usable (the memo commit that stores the call's token decides to abort, so a rerun after a crash skips the abort instead of stopping newer work); a child's Session also stops by itself once it settles with nothing pending, and every message to it attaches it again while it lands (see `DurableThreads` below). `list` shows state, saved Agent, model, and Session. Only the caller's own children are reachable by name. Request IDs make a restart deliver each once: `oppi-spawn:<reporterTaskId>` (the child's first task), `oppi-report:<childConversationId>:<answerEntryId>` (the report of an answer, whichever reporter posts it, so `wait` can find it), `oppi-report:<reporterTaskId>` (a reporter's failure report), and `oppi-send:<callerStoreId>:<callerConversationId>:<toolTaskId>` (`send`, submitted by its reporter). They are reserved in `durable-request-ids.ts`. The message and report inputs are placed as `oppi.agent-message` entries (pi-durable `InputEntry`, `extensions/durable/sessions/agent-message.ts`) whose data names the sending session and intent, plus the length of a model-only header; the model message stays the plain user message. Trace projection and the live `message_end` turn that data into `origin` on the user event and drop the header from its text. Tool `details` carry `{ name, conversationId, sessionId }`; `wait` and `list` carry one per child in a `children` array (`list` omits `sessionId` while the Session is pending). The children's widget pill is described in `durable-extension-ui.md` ("Subagent pill").

Nesting follows `oppi session create`'s rules through one function (`childDelegationGrant` in `agent-launch-service.ts`): a top-level session may spawn; a child may spawn only when it holds the `allowNestedDelegation` grant, which passes down its subtree; a sandbox parent's children stay in its sandbox and cannot receive the grant. The grant lives on the child's `oppi.agent` document (`spawn`, `grant`) and is copied to its row's `launch.allowsNestedDelegation`. Without it the `oppi.sessions` extension is removed from the child in the same `configure`, and an attach of the child removes it again from the host default selection. A grandchild is a conversation owned by a task of the child in the root's store, and its row's parent is the child.

One resolver turns a saved Agent (or none) into the conversation's agent: `resolveDurableAgent` (`durable-agent.ts`) returns pi-durable's `AgentChange` plus the `oppi.agent` document. `subagent spawn` and a top-level durable launch (`DurableBackend` creating its conversation, after `AgentLaunchService` and schedules recorded the Agent on the row and `meta.json`) both commit it with the new conversation. The mapping: `sessionDefaults.model`/`thinkingLevel` to `model`/`thinkingLevel` (explicit ones win); `tools`/`excludeTools`/`noTools` to an exact `tools` list and the document's tool policy, with Pi's semantics (`toolAllowed`): an allow list is the enabled set, `noTools: "all"` without one enables nothing and skips MCP, `"builtin"` drops only Pi's built-in tool names and keeps extension and MCP tools, and `excludeTools` always applies; `resources.extensionIds` to `extensions`, by the classic Extension IDs of each Pi package that has a durable entry for the runtime (`resolveDurableExtensionSelection`: `builtin:mcp` is the session's MCP and `builtin:tool-search` comes with it; an ID of a user package the loader skipped because a built-in already is it, such as the link to `pi-extensions/ask`, is that built-in (`DurableHarness.classicExtensions`); anything else without a durable entry, `builtin:codemode` among them, is left out and named in the document's `extensions.skipped`, which each attach records as one `Session.warnings` entry and a `durable_agent.extensions_skipped` log line, as classic records dropped Agent tools); `skillPaths`/`agentsFiles`/`noContextFiles` to the document's `resources`, which the project-context sections load (`loadDurableProjectResources`: a host session uses Pi's `DefaultResourceLoader`; a sandbox session ensures the workspace VM first, before the conversation exists, and discovers only through that attachment's `GondolinExecutionEnv`, which `/reload` reuses: each mounted `.pi/skills` entry and the workspace's `.agents/skills`, walked by Pi's rules over the VM's listing and stat, the context file at the guest root, every byte through the VM's shadowed, jailed provider with a 1 MiB cap (`SANDBOX_RESOURCE_MAX_BYTES`; larger files are skipped and logged), and frontmatter through Pi's `parseFrontmatter`. Project `.pi/settings.json` Skill filters and ignore files are not applied there. Selected `skillPaths` map lexically to guest paths and must name a discovered Skill, else `agent_skills_unavailable`; saved AGENTS files are kept only inside the workspace, at guest paths, redacted); `instructions` to `instructions`, where replace also sets `projectContext: false` and the `project_context` section stays empty; name, icon, description, id, and version to the document's `agent`, which the child row's launch fields copy. No Agent: the child copies its parent's agent and document, with its own delegation, minus the parent's MCP extension. Launch constraints that exclude the parent's workspace or runtime refuse the spawn with the `oppi session create --agent` command to start it top-level instead. After launch nothing reads the definition again: an attach reads the `oppi.agent` document (exact package selection, MCP on or off, resources, delegation), so editing an Agent changes later launches, not running sessions.

A full Stop of a session (not a composer abort) also aborts its `oppi.session-reporter` tasks (`DurableHarness.abortSessionReporters`), so a stopped parent gets no new turn from a background child's report; the child and background shell jobs keep running. `DurableThreads` (`durable-threads.ts`) gives each owned child its Oppi Session: created exactly once, keyed by the child conversation id (launch idempotency key `durable-thread:<conversationId>`), bound through `serverDurable.conversationId` with the parent's workspace and worktree, the saved Agent, tool policy, and grant from its `oppi.agent` document, and attached, so a restart finds it in `resumeIds`. Its launch sets `autoStop`, as `oppi session create --auto-stop` does, since an idle conversation costs nothing and takes messages later: `SessionLifecycleCoordinator.handleSessionSettled` stops the child once it settles ready with no pending user-reply dialog and no pending wake (`hasPendingWake`: its undelivered background jobs and its own reporters), which releases its `DurableBackend` attachment, sandbox env, and MCP servers. With a pending wake it stays until the turn that wake starts settles; auto-stop sessions now also keep the idle timeout, so a wake that ends without a turn stops the child later. Rows created before this have no `autoStop` and keep only the idle timeout. `materialize` only creates and binds the row. Every submission to a child goes through `DurableSessionsHost.activate(sessionId, submit)` (`DurableThreads.activate`, `SessionManager.withIncomingWork`): a background spawn's and each `send`'s reporter when it delivers its message, a foreground spawn's task, and `wait` for a message no reporter delivered yet; a `wait` with nothing to deliver reads the stopped child from the store, and opening the child from the pill is an ordinary `startSession`. From the call until `submit` settles the session counts that incoming work; a stop already under way (pending `terminate`) finishes first and the session starts again before `submit` runs. The auto-stop checks the wake asynchronously, then under the session lock reads the backend (`hasPendingWork`: a live run or queued input, from the store, since the store commits input before the session's projected status sees its run; and `hasPendingWake` again), and with no await after that rechecks the incoming-work count, the status, and dialogs and marks the stop pending in the same section. Incoming work announced before that section keeps the child; work announced after it waits for the stop. When the count drops to zero on a ready session, auto-stop decides again: the work either started a run, which the store read sees and which settles later, or never came (its caller was aborted, or the message was already answered), and the child stops. Events after a settle that start no work (a trailing custom message) no longer cancel the decision; the locked recheck decides. A child that cannot be attached (its VM does not boot, its workspace is gone, limits) is not an error of the reporter's phase, which pi-durable would fault for good: the reporter reports `[session <name> (<id>) failed: could not start: <reason>]` to the parent and ends, `wait` returns that reason for the child, and a foreground spawn fails its call. When the server is stopping (`startSession` refuses during shutdown before the store closes), the caller instead waits for its task's abort, so the task stays pending and runs again after the restart. A stopped child is not on the restart-resume queue, so a restart leaves it stopped and its conversation unchanged until the next message. It stopped with no pending waker, so the store fence (`fenceStopped`, which aborts leftover tasks of conversations whose rows are neither active nor queued) finds at most its working-words ticker, which the next attach starts again; no job or reporter of it is lost. A row already holding that key is adopted only when it is bound to that same conversation; otherwise the spawn fails, and session create routes reject `durable-thread:` keys from clients. `launch.parentSessionId` is a write-once copy of the ownership edge. `GET /sessions/:id/thread` for a durable session adds the sessions its ownership edges put in the thread (`scanConversations({ ownerConversationId })`, from the topmost owner down; when that owner's Session is gone, the thread roots at the nearest remaining ancestor Session) to the launch-edge tree, so a child belongs without a launch edge and a session the phone starts in the thread still joins through its launch edge; the response shape is unchanged. Classic sessions keep the launch-edge tree and `session_interactions`.

The durable control conversation is one Session row per data directory, marked `serverDurable.role: "control"` and bound to its conversation id, created on demand by `POST /control-conversation` (`oppi control open|send`) through `ControlConversationService` under the reserved launch key `control-conversation`. It selects an exact extension array (`controlConversationExtensions`: `ask`, `working-words`, `oppi.control`, `codemode`), never `DurableHarness.defaultExtensions`, re-asserted on every attach, and runs in the owner-only `$OPPI_DATA_DIR/control-conversation/cwd`. Idle, it is on the restart-resume queue and comes back after a restart. It is on the phone's global recent list with declared control sessions, never in a workspace catalog or count, and the phone opens it through the same `/control-sessions` routes. List rows carry `serverDurable.role` so the client can tell it from a workspace durable session; the conversation id stays off that projection. `oppi.control` (`server/extensions/durable/control/durable.ts`) registers one ordinary durable tool per row of one table: `oppi({ argv })` and typed tools (`agents_list`, `agents_create`, `schedules_run`, `sessions_send`, …) that only build argv, each with its input and structured output schema. The model calls them directly, and the selection's pi-durable `codemode` extension (`DurableHarness.controlCodemode`: one `CodemodeSandbox` with a 256 MiB VM memory limit, `models: false`) lets scripts call them as `tools.<name>`, each a nested tool call. `DurableControlCli` (`server/src/durable-control-cli.ts`, bound with `DurableHarness.bindControl`, reached through `oppiHost().control(env)`, which only the control conversation's env gets) is the host the extension cannot import. It refuses argv that reaches the host without a request or would hurt the server it runs in (file flags, `@-`, `config set`, `--config-file`, the `control` family, which would message the conversation from inside its own turn, `status`, which shells out synchronously on the event loop, and the `--idempotency-key=`, `--request-id=` and `--turn-id=` forms, which the CLI ignores and the host cannot tell from a script's own key). For `agent create`, `session create`, `schedule create` (`--idempotency-key`), `schedule run` (`--request-id`), and `session send` (`--turn-id`) it makes `<tool call task id>:<hash of the call's argv>` the only replay key, replacing any key the caller passed. It runs `runCli` with `forceJson` and `captureHuman` inside `withLocalApiInterceptor`. The interceptor throws on a non-GET for a read tool; for a write tool it awaits the extension's confirm card, a `select` through `requestUI` keyed by the call's task and the write's place in the command (Yes / No for a direct call; Yes / Yes to all remaining in this script / No inside a script). Cards of one script, or of one conversation's direct calls, are asked one at a time, so "Yes to all" (`oppi.control-approval` on the script's own task, retired with it) covers the writes waiting behind it; the next script asks again. A PATCH card carries a diff against the record the host fetches. The gate is fixed in code. Every control tool is `replay: "safe"`. pi-durable's codemode replays a script after a restart from its journal: finished calls get their recorded results and never run again, and an interrupted call reruns with the same arguments, the same replay key, and its saved card answer, so a keyed write is answered from the store and no second card is asked. A confirm card shows the whole request body; a body over 6000 characters is refused (error `body_too_large`, nothing asked or sent) instead of truncated. Codemode scripts have no deadline unless they set `timeout_ms`, so an unanswered card or a long `sessions_wait` is not cut short. The `oppi-control` prompt section holds the role and guidance; tool declarations come from the tools and from the `codemode` section.

Replay is exactly-once only for the five keyed commands above (`session start` is `session create`). The key is the tool call's task id with a hash of its argv; a codemode rerun reattaches each nested call to its task by key, whatever order calls complete in, so a keyed write that landed is answered from the store. Each confirm card's request (method, path, body) is kept with the call before the card is asked (`oppi-card:<slot>`, first write wins). A rerun that builds a different request at that slot, for example a workspace or session name that now resolves elsewhere, fails with `card_changed` and sends nothing, also under "Yes to all", so a saved answer never approves another write. A repeated `clientTurnId` (what `--turn-id` becomes) is deduplicated by a durable conversation from its stored submission, which survives a server restart; a classic session dedupes it in the in-memory turn cache (15 minutes, 256 entries), which a restart loses. Residual risks:

- `agent update` and `agent archive` have no replay key. After a crash between the write and the call's result, the rerun reports a false failure (a version conflict, or 404 for an archived Agent); with `expectedVersion` the patch is not applied twice, so callers should pass it. Without it an `append` instruction patch applies twice.
- Writes through `oppi(...)` that have no key (workspace and worktree create or open, dictionary add, schedule update) can be applied again after a crash in that window.
- A transport error after the server applied a write is memoized as a failure, so a rerun does not retry it with its key.
- `config show|get|validate` build a `ConfigStore` that may rewrite `config.json` under a synchronous spin lock of up to about 5 s on the server's event loop.
- Replay keys are not scoped to one durable store. If the durable database were reset while the Agent and Schedule stores kept their data, a new task could reuse an old key with the same argv and get an old record back.
- Confirm cards are answered with owner or paired-device credentials as `extension_ui_response`, over the WebSocket `/control-sessions/<sessionId>/stream` or `POST /control-sessions/<sessionId>/command` (and `POST /sessions/<id>/command`); `GET /sessions/<id>/dialogs` lists the pending card and its id. The phone lists the row with declared control sessions and answers the card with the existing select dialog. There is no CLI verb for the answer.
- The confirm card guards against the control model, not against other local processes that hold the owner token: those could write through the API directly anyway.

This slice has a minimal coding prompt plus workspace and saved-Agent instructions. Classic extensions, tree navigation, and entry renderers are unavailable. `reloadResources` loads AGENTS files and saved-Agent skillPaths; it does not load classic extensions, prompt templates, or themes. Queue editing is a full replacement of steer and follow-up inbox items: removed submissions settle `unanswered`/`aborted` so the original send stays quiet, write items stay queued, and a boundary that places an item during the edit rejects the stale save. The edit does not start a turn. Idle sessions still cannot gain a queue from nothing, and an idle rewrite waits for the next real admission, which places writes before the new input. Fork uses the Durable `conversation.fork(entryId)`: `get_fork_messages` lists user-message entries by their decimal Durable entry ids (the ids of the trace's user rows), and the fork route creates a new bound Session on a forked, ownerless conversation that keeps the source's execution runtime. As in classic fork, the branch point is the visible entry before the chosen user message, so the fork's transcript ends before it (the phone does not read the message text back as editor text). Forking at the first user message has no earlier entry, so it creates a fresh ownerless conversation with the source's stored agent and runtime. A durable source never falls back to a Pi JSONL fork. Unsupported backend operations throw `DurableNotSupportedError` (`server_durable_not_supported`): `sessionTree` and `navigateTree` (a conversation has no in-place leaf; navigating would fork and rebind the session, which drops the later turns from the tree, cannot summarize the abandoned branch, and leaves the old conversation's background work behind, so the existing fork-from-a-message is the supported way back), `abortBash` (classic aborts only a user-started shell command, which the server never starts on either engine; `abort` stops a model's bash tool), `appendAssistantMessage` (the synchronous E2E UI harness fixture seam), and `replaceQueuedModelTurns` / `clearQueuedModelTurns` (classic's in-memory queue; durable uses the native inbox operations, which `abortClearsQueuedModelTurns` and `nativeMessageQueue` route around, so no supported path reaches them). `exportToHtml` (and so Share) feeds the conversation's entries from `durable-history.ts` to Pi's `exportSessionToHtml` through a private temporary JSONL (`durable-export.ts`, loaded from Pi's dist like `pi-mcp-internals.ts`); system sections leave the chain because the page shows `systemPrompt`, and a compaction exports as a `custom_message` with its summary because the page formats a compaction's `tokensBefore`, which durable does not record. `persistsWithoutSessionFile` lets Share skip its Pi session-file guard. `setAutoRetryEnabled`, `setAutoCompactionEnabled`, `setSteeringMode`, and `setFollowUpMode` write the `SettingsManager` that `harnessSettings` reads live (`DurableHarness.runPolicySettings`), the same global user settings a classic session writes: they are not per session, and a classic session that already loaded its settings does not see them until it reloads. `abortRetry` marks the generation task abort-requested in one commit that first checks the task's checkpoint is still `phase: "retry"` (the backoff is a durable sleep there, which the mark ends at once) and `pi.live.generation.retry` is set, then waits for the task (`waitForTask`), so the command returns after the run has settled `unanswered/aborted` and the projection has emitted `retry_end` with the last error. If the backoff already ended, the commit does nothing and the next attempt runs on, as classic (which only aborts the sleep); outside a backoff it does nothing either. pi-durable's public `Tx` cannot write the mark, so the commit calls `Tx.setTask`, the call `harness.abortTask` makes itself, and fails loudly if a later pi-durable drops it. Queued inputs then stay in the inbox (Stop withdraws them) and do not start: after an aborted run pi-durable places the inbox only on the next submission, and offers no public way to start it, so the next message the user sends places them, oldest first; classic's agent loop would deliver them at once. After a run that fails (`model_error` or `no_model`, including retries exhausted), the queued inputs start the next run, as classic does, behind the run's failure card. pi-durable's `afterFailedRun: "continue"` would place them in the commit that fails the run, ahead of the card, which Oppi writes in a later commit, so the Harness keeps the default (`keep`): once `DurableBackend` has written the card, `DurableAgentController.continueAfterFailedRun` admits a hidden write (`oppi.continue`, no model message and no card, with `edits: []` so it is not display-only and request id `oppi-continue:<failed input>`), whose final boundary places it and then the queued inputs and starts the run. The event projection holds the failed run's `agent_settled` meanwhile, and a run that hands over in the same commit (a final answer with queued inputs) holds it too, so the session settles once, after the last run, as classic does, and `launch.autoStop` cannot stop it between them. A failure the session's backend does not see (no attached session, or a crash before its card) leaves the inputs queued until the next message. Incognito sessions, and saved-Agent Extension selections without a durable entry, are rejected rather than silently losing those guarantees. Apple history paging and outline read Durable entries. `compact()` is implemented; full compaction detail parity remains outside this slice. Turning the flag off rejects new durable requests; already-bound Durable sessions keep resuming on Durable without it, and a durable request that never bound a conversation starts classic with a session warning.

## Saved Agents and schedules

Saved Agent routes persist reusable user definitions. The Agents client presents Pi separately, without an `agent_definitions` row. Launch-time inputs such as workspace, worktree, prompt, model override, and session name flow through `AgentLaunchService`, which owns idempotency, launch recovery, target-constraint enforcement, and prompt dispatch into managed sessions. Definitions may restrict launches to allowed workspace IDs and a required host or sandbox runtime. Incompatible targets and unavailable selected Skills or Extensions fail closed as typed configuration failures. Allowed tool names that no active tool matches at launch are dropped from the session's effective tool set and surfaced through `session.warnings`, so an unavailable allowlist entry cannot block the whole launch; the saved definition is not rewritten. Pre-start checks may discard a never-announced empty shell and return an actionable non-retryable `422` without a session ID; failures after runtime start preserve one `error` session for audit. Focused streams close with policy violation rather than reconnecting and duplicating timeline errors.

A server-scoped Pi Control session persists explicit `domain`, `intent`, and optional target metadata with no `workspaceId`. Creation may set model and thinking overrides, while a user-selected workspace remains prompt context rather than runtime ownership. `/control-sessions` routes admit a declared control session or the durable control conversation before reusing the ordinary lifecycle, trace, attachment, command, broadcaster, and focused-stream services. Generic `/sessions/:id/command` and `/sessions/:id/stop` admit those same sessions and share the same lifecycle and caller-interaction recording. Both remain in the global recent projection but never enter workspace catalogs or counts. An idempotent launch persisted as `promptDispatch: not_sent` may claim a compare-and-swap lease and retry its frozen initial prompt. A launch left `launching` after process failure is conservatively not redispatched even after lease expiry, because existing persistence cannot distinguish a crash before send from one after Pi accepted the turn. Agent, Schedule, Workspace, Skill, and Theme revisions use explicit control domains rather than inferring authority from a missing workspace. Pi Control loads normal global `SYSTEM.md`, `APPEND_SYSTEM.md`, settings, tools, Skills, prompt templates, and Extensions. It has ordinary host-user permissions and can run the installed `oppi` CLI through `bash`; Oppi does not add a separate tool approval layer.

The CLI accepts bounded in-memory `--definition-json` objects for Agent create/update and schedule update, avoiding temporary files for those domains. Canonical Agent and schedule validators reject unexpected fields and empty updates at the server boundary. Skill revisions instead use stock `read` and `edit` on the selected existing absolute host path. The `oppi skill` CLI family and Skill-file HTTP PUT route do not exist; catalog editability remains presentation metadata, not a stock-tool authorization boundary. Theme sessions also use stock `read`, `write`, and `edit`: a revision receives the absolute path `GET /themes` reports for the served file, and saves its result to the data-dir `themes` folder, which overrides bundled and Pi TUI themes with the same filename. The theme HTTP routes stay read-only.

Schedules persist a trigger plus an action. `AgentScheduleRunner` scans active schedules, materializes due slots, claims due runs with a lease, and dispatches automatic runs through the same launch hooks used by manual schedule runs. Pause or archive a schedule to stop future automatic runs. Archived schedules remain listable and can be restored directly to active.

## Terminal mirror runtime

`PiTuiMirrorRuntime` owns `/mirror/v1/bridge` and implements the same `AgentRuntimeTransport` interface as the managed runtime. It registers terminal bridges, resolves the workspace, coalesces sessions by Pi identity, handles takeover confirmation, forwards remote commands, proxies extension UI, mirrors queue state, and projects terminal Pi events through the shared session event pipeline.

Mirror sessions are terminal-owned. If the bridge disconnects, the stored session remains `runtime == "pi-tui"` unless the app explicitly resumes a stopped disconnected session as an Oppi-managed runtime.
